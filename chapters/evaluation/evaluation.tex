\section{Evaluation Methodology}
\label{sec:evaluation}

This chapter details the methodology used to evaluate the \textbf{Agentic Project Management (APM)} framework. To assess the framework's effectiveness against current industry standards, we conducted a comparative case study involving human participants.\newline

\noindent The evaluation was designed to measure three distinct dimensions:

\begin{itemize}
    \item \textbf{Economic Efficiency} \placeholder{cost framing pending lit review}
    \item \textbf{Process Efficiency} (human cognitive load and interaction burden)
    \item \textbf{Functional Efficacy} (ability to complete non-trivial tasks)
\end{itemize}

\subsection{Research Objectives}

The primary objective of this research is to determine whether the structural overhead introduced by APM \placeholder{phase names pending APM v1 terminology update in Phase 2} yields a tangible return on investment compared to a single-agent workflow.\newline\newline
We define the following Research Questions (RQs):

\begin{itemize}
    \item \textbf{RQ1 (Economic Efficiency):} \placeholder{cost framing pending lit review — to be reframed around request consumption / resource efficiency rather than raw token cost}
    \item \textbf{RQ2 (Process Efficiency):}
    \begin{itemize}
        \item Does the structured coordination of APM reduce the "human burden" during execution? Specifically, does it reduce the need for user interventions, corrections, and clarifications?
        \item Is the reduction in human burden due to the structured coordination of APM significant enough to justify the structural overhead?
        \item Are the agents able to effectively coordinate and complete the task without the need for constant human oversight?
    \end{itemize}
    \item \textbf{RQ3 (Functional Efficacy):}
    \begin{itemize}
        \item Can APM successfully deliver complex, non-trivial features in scenarios where unstructured agentic workflows typically encounter "Agentic Handoff Failures"?
        \item How does the performance of APM compare to the performance of a single-agent workflow?
    \end{itemize}
\end{itemize}

\subsection{Testbed and Task Design}

To evaluate the frameworks under realistic constraints, we utilized an existing open-source project, the \texttt{eclass-mcp-server}, a Python-based Model Context Protocol (MCP) server designed to interface with the \texttt{openeclass} platform. Openeclass is an online platform for Greek universities that allows students to manage their courses and assignments.

\subsubsection{The Task:}

The final task requires participants to implement a new \texttt{get\_course\_announcements} tool in the Python MCP server and, crucially, to create a complete native C replica of the MCP server. The task specification was refined through iteration to ensure sufficient complexity for differentiating multi-agent from single-agent approaches.\footnote{Task specification and grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task}}\newline

\noindent This C implementation adds significant complexity, turning the assignment into a challenge of managing code translation, memory safety, and protocol details across two very different languages. As such, the task is specifically designed to stress-test the limits of agent coordination and reveal differences between multi-agent and single-agent approaches, especially in scenarios where context management becomes a bottleneck.\newline

\noindent \textbf{Key Technical Challenges:}

\begin{enumerate}
    \item \textbf{Dynamic Data Source:} The required data for implementing the new feature is not available in static HTML for parsing. Agents must research the legacy codebase to discover a specific AJAX endpoint and its behavior.
    \item \textbf{Nested Parsing:} The server returns JSON where the payload is an array of raw HTML strings, requiring a second layer of parsing to extract the data.
    \item \textbf{Client-Side Filtering:} The legacy API does not support date filtering. The agent must implement robust client-side logic to parse and filter unique locale-formatted dates.
    \item \textbf{C Implementation:} Agents must build a native C MCP server replica, manually implementing JSON-RPC 2.0 with standard C string manipulation (no external JSON libraries such as cJSON/Jansson). Use of \texttt{libcurl} for HTTP/HTTPS and \texttt{libxml2} for HTML parsing, was required for the eclass MCP server functionality.
    \item \textbf{Memory Safety:} The C implementation must be memory-safe, passing Valgrind checks without leaks or errors.
\end{enumerate}

\noindent \textbf{Deliverables:}

\begin{enumerate}
    \item Core server logic in modular Python files (existing and new functionality).
    \item A native C implementation of the MCP server with equivalent (existing and new) functionality.
    \item A working build system (Makefile) for the C replica.
\end{enumerate}

\subsubsection{Grading:}

Submissions are evaluated using an automated black-box test suite with comprehensive validation, grading, metric extraction, and dataset aggregation capabilities (see the evaluation appendix for detailed infrastructure documentation).\footnote{Grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task/tree/main/grader}} \newline

\noindent The test suite awards \textbf{48 points total}: 12 points for baseline functionality (existing Python tools), 12 points for the new Python feature (\texttt{get\_course\_announcements}), and 24 points for the complete C replica implementation. A submission with no patch applied receives the baseline score of \textbf{12/48 points}.\newline

\noindent All tests are run against fixed baseline commits to ensure reproducibility: \texttt{eclass-mcp-server} at commit \texttt{8b4e39c} and \texttt{openeclass} at commit \texttt{e8b3329} (Docker image \texttt{openeclass:test}). 

\subsubsection{Repository Architecture and Data Management}

The case study employs a two-repository system separating public resources from sensitive participant data. The \textbf{task repository} (\texttt{bsc-apm-case-study-task}) is openly accessible and includes task specifications, grading infrastructure, and participant guides. The \textbf{dataset repository} (\texttt{bsc-apm-case-study-data}) contains all submitted participant data: code patches, sanitized chat transcripts (see Section~\ref{sec:sanitization}), and anonymized session metadata.\newline

\noindent Access to the dataset repository's secret access key requires explicit authorization and compliance with data usage agreements. This controlled access mechanism enables peer review and reproducibility while maintaining participant privacy protections.

\subsubsection{Sanitization and PII Handling}
\label{sec:sanitization}

Chat exports contain sensitive information (unstructured user-input text, file paths, command histories, timestamps). To protect participant privacy while enabling reproducibility, all exports are sanitized using reversible encryption before storage. \newline

\noindent Each chat is assigned a unique identifier via SHA256 hashing of concatenated user messages for anonymous cataloging. Essential metadata (chat ID, model IDs, request count) is preserved in plaintext to enable dataset organization without decryption, while conversation content is encrypted using an HMAC-SHA256 XOR cipher. The same sanitization method is applied uniformly across both platforms. \newline

\noindent For detailed technical specifications of the anonymization and encryption processes, see the evaluation appendix.

\subsection{Learning Effects and Confounding}

\textbf{Critical Issue:} Participants complete the same task twice (Session 1 and Session 2) using different frameworks. This creates a learning effect where task familiarity from S1 influences S2 performance, potentially confounding framework comparisons.

\noindent \textbf{Analysis Strategy:}
\begin{itemize}
    \item \textbf{Learning Effect Matrix:} Calculate mean improvement (percentage change) from S1 to S2 for both S1→S2 framework combinations across all metrics (functional scores, cost, process efficiency)
    \item \textbf{Order Effect:} Compare APM→Spec-kit vs. Spec-kit→APM directions. Tests whether order of framework exposure affects learning.
    \item \textbf{Baseline Learning:} Overall mean improvement across both directions (pure task learning effect regardless of framework)
\end{itemize}

\noindent \textbf{Key Questions:} Does task learning confound framework comparisons? Is there a "best first framework" that maximizes S2 improvement? How do we control for learning effects when comparing frameworks?
