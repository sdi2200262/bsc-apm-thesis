\section{Evaluation Methodology}
\label{sec:evaluation}

This chapter details the methodology used to evaluate the Agentic Project Management (APM) framework. To assess the framework's effectiveness against current industry standards, we conducted a comparative case study involving human participants. The study compares APM, a multi-agent framework that distributes work across specialized agents, against GitHub Spec-kit, a single-agent toolkit that guides one AI agent through a structured specification-driven workflow. Both frameworks are described in Section~\ref{sec:frameworks}.

The evaluation measures three distinct dimensions:

\begin{itemize}
    \item Economic Efficiency (share of the Copilot monthly request allowance consumed per session)
    \item Process Efficiency (human cognitive load and interaction burden)
    \item Functional Efficacy (ability to complete non-trivial tasks)
\end{itemize}

\subsection{Research Objectives}

The primary objective of this research is to determine whether the structural overhead introduced by APM (i.e., the Planning and Implementation phases) yields a tangible return on investment compared to a single-agent workflow. Prior empirical work on AI coding assistants has concentrated on productivity and task-completion time \citep{pengetal2023, cuietal2025, paradisetal2024, ziegleretal2024, vukovicetal2026}, with comparatively little systematic treatment of cost under the subscription-based procurement model through which Copilot is predominantly adopted. This evaluation contributes a cost perspective alongside the process and functional dimensions.

\newpage

We define the following Research Questions (RQs):

\begin{itemize}
    \item \textbf{RQ1 (Economic Efficiency):}
    \begin{itemize}
        \item Under GitHub Copilot's subscription-plus-quota pricing structure, does APM's multi-agent coordination consume fewer premium requests per session than Spec-kit's single-agent workflow?
        \item If a difference in request consumption is observed, is it large enough to meaningfully shift the share of a buyer's monthly allowance burned per task completion?
        \item Where in each framework's workflow (planning phase versus implementation phase) does request consumption concentrate, and does that concentration pattern differ between frameworks?
    \end{itemize}
    \item \textbf{RQ2 (Process Efficiency):}
    \begin{itemize}
        \item Does the structured coordination of APM reduce the amount of manual effort the user must invest during execution, particularly interventions, corrections, and clarifications?
        \item If a difference in user effort is observed, is it significant enough to justify the structural overhead APM introduces?
        \item Given that the User remains in the loop as a message carrier, can the agents coordinate effectively enough that the User's role stays limited to shuttling messages rather than correcting or redirecting agent behavior?
    \end{itemize}
    \item \textbf{RQ3 (Functional Efficacy):}
    \begin{itemize}
        \item Can APM successfully deliver complex, non-trivial features in scenarios where single-agent workflows are prone to failure due to context exhaustion, loss of coherence across long sessions, or inability to coordinate work across multiple concerns?
        \item How does the performance of APM compare to the performance of a single-agent workflow?
    \end{itemize}
\end{itemize}

\subsection{Frameworks Under Evaluation}
\label{sec:frameworks}

The two frameworks are both open-source and spec-driven, running on the same AI IDE platform. Both structure work through explicit specification and planning artifacts before implementation begins. They differ in how execution is organized: Spec-kit operates within a single agent conversation, while APM distributes work across multiple specialized agents.

\subsubsection{GitHub Spec-kit}

Spec-kit\footnote{Documentation available at: \url{https://github.github.com/spec-kit/}} is a specification-driven development toolkit developed by GitHub. It guides a single AI agent through a structured workflow using three sequential commands:

\begin{enumerate}
    \item \texttt{/speckit.specify}: transforms a feature description into a structured specification containing requirements, user stories, and acceptance criteria.
    \item \texttt{/speckit.plan}: converts the specification into a technical implementation plan with architecture decisions, data models, API contracts, and supporting documents.
    \item \texttt{/speckit.tasks}: derives an executable task list (\texttt{tasks.md}) from the plan, with parallelism annotations and sequencing constraints.
\end{enumerate}

Execution is triggered by a fourth command, \texttt{/speckit.implement}, which parses the task list and carries out each task in sequence. Additional commands support iterative refinement (\texttt{/speckit.clarify}), cross-artifact consistency checking (\texttt{/speckit.analyze}), and custom quality checklists (\texttt{/speckit.checklist}). A constitution mechanism, maintained via the \texttt{/speckit.constitution} command, allows users to establish architectural rules that the agent enforces throughout the workflow.

All planning and implementation happens within one continuous conversation. The agent acts as both planner and executor, and the full specification, plan, and task context accumulates in a single context window. Spec-kit produces a fixed set of artifact types (specification, plan, data model, contracts, research, tasks) regardless of project type; the templates are predefined and every project receives the same artifact layout.

\subsubsection{APM in Comparison}

Where Spec-kit runs the entire workflow in a single conversation, APM (described in detail in the preceding chapters) separates planning, coordination, and execution across three agent roles, each operating in its own conversation with deliberately scoped context. Agents communicate through a file-based Message Bus rather than sharing a context window, planning documents adapt their structure to the project rather than matching to a predetermined artifact layout, and the user acts as a message carrier between conversations. When an agent's context fills, an explicit Handoff mechanism preserves working knowledge across context boundaries.

The evaluation tests whether this multi-agent overhead produces measurably better outcomes than Spec-kit's single-agent approach. The task is designed to be complex enough to challenge a single context window, making it a meaningful test of whether distributing work across specialized agents with scoped context yields tangible benefits in practice.

\subsection{Testbed and Task Design}

To evaluate the frameworks under realistic constraints, we utilized an existing open-source project, the \texttt{eclass-mcp-server},\footnote{Repository available at: \url{https://github.com/sdi2200262/eclass-mcp-server}} a Python-based Model Context Protocol (MCP)\footnote{Protocol specification available at: \url{https://modelcontextprotocol.io}} server designed to interface with the \texttt{openeclass} platform.\footnote{Repository available at: \url{https://github.com/gunet/openeclass}} Openeclass is an online platform for Greek universities that allows students to manage their courses and assignments.

\subsubsection{Task Description}

The task requires participants to implement two new announcement tools in the Python MCP server and to create a complete native C replica of the entire server.\footnote{\raggedright Task specification and grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task}} The two tools are:

\begin{itemize}
    \item \texttt{get\_course\_announcements}: retrieves announcements for a specific course.
    \item \texttt{get\_general\_announcements}: aggregates system-wide and per-course announcements.
\end{itemize}

The C implementation adds significant complexity: participants must manage code translation, memory safety, and protocol details across two very different languages. This combination of feature implementation and full-language replication is calibrated to stress-test the limits of agent coordination and expose any differences between the two frameworks, especially when context management becomes a bottleneck.

Key technical challenges:

\begin{enumerate}
    \item Dynamic Data Source: the required data for implementing the new features is not available in static HTML for parsing. Agents must research the legacy codebase to discover a specific AJAX endpoint and its behavior.
    \item Nested Parsing: the server returns JSON where the payload is an array of raw HTML strings, requiring a second layer of parsing to extract the data.
    \item Client-Side Filtering: the legacy API does not support date filtering. The agent must implement robust client-side logic to parse and filter unique locale-formatted dates.
    \item C Implementation: agents must build a native C MCP server replica, manually implementing JSON-RPC 2.0 with standard C string manipulation (no external JSON libraries such as cJSON/Jansson). Use of \texttt{libcurl} for HTTP/HTTPS and \texttt{libxml2} for HTML parsing was required. A working Makefile must build the C binary.
\end{enumerate}

\subsubsection{Grading}
\label{sec:grading}

Submissions are evaluated using an automated black-box test suite with comprehensive validation, grading, metric extraction, and dataset aggregation capabilities (see the evaluation appendix for detailed infrastructure documentation).\footnote{Grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task/tree/main/grader}}

The test suite awards 100 points total: 12 points for baseline functionality (existing Python tools), 36 points for the two new Python features (18 points each), and 52 points for the complete C replica implementation. A submission with no patch applied receives the baseline score of 12/100 points.

All tests run against fixed baseline commits to ensure reproducibility: \texttt{eclass-mcp-server} at commit \texttt{8b4e39c} and \texttt{openeclass} at commit \texttt{e8b3329}.

\subsection{Study Design}

The study is conducted on a single AI IDE platform, VS Code with GitHub Copilot, and compares the two frameworks across a homogeneous cohort of participants. It is designed as a within-subjects experiment, so that each participant contributes data points for both frameworks and per-participant variance in skill, prior experience, and working style is absorbed into each pairwise comparison rather than confounding it.

\subsubsection{Experimental Design}

Each participant completes the case study task twice: once with APM, once with Spec-kit. The order of the two frameworks is counterbalanced across participants, so that approximately half of the cohort encounters APM first and the other half encounters Spec-kit first. This counterbalancing lets us attribute any observed first-to-second session improvement to task familiarity rather than to the framework itself, and is analyzed explicitly in Section~\ref{sec:results} under Learning Effects.

The two sessions are isolated from one another using Git, so no code, state, or context from the first session can influence the second. The participation workflow including session isolation and patch submission are documented in the evaluation appendix.

\subsubsection{Data Source}

The primary data source for the study is GitHub Copilot chat exports, captured in JSON form from the VS Code Command Palette at the end of each session, alongside each participant's patch submission. Copilot's export format provides structured records of every conversation, including model identifiers, message timestamps, tool invocations, and per-message speaker roles. This granularity enables programmatic extraction of both request-level and interaction-level metrics directly from the exports, without manual annotation. Because GitHub Copilot is billed per seat with a monthly premium-request allowance and a marginal per-request charge for overage consumption, the per-conversation request counts preserved in the export metadata correspond directly to the unit in which the buyer's cost is incurred.\footnote{Premium-request billing structure and overage rates documented at: \url{https://docs.github.com/en/billing/concepts/product-billing/github-copilot-premium-requests}}

APM's multi-agent workflow spans multiple Copilot conversations within a single session (one for the Planner, one for the Manager, and multiple for the Workers), while Spec-kit operates within a single conversation. To keep the two frameworks comparable, all metrics are computed by aggregating every conversation file belonging to a participant submission into a unified session-level view, so that the total interaction cost of the session is captured regardless of how the work was distributed across conversations.

\subsubsection{Participant Pool}

Participants are drawn from a cohort of University students and working professionals with active access to GitHub Copilot, either through the GitHub Education Pack or through a standard premium subscription.

\subsection{Metrics and Data Collection}
\label{sec:metrics}

The metrics collected for this study are organized into five categories: session metadata, the three dimensions introduced above (economic efficiency, process efficiency, and functional efficacy), and the functional grading rubric. The subsections below specify each category in turn.

\subsubsection{Cost Metrics}

GitHub Copilot is billed as a three-part tariff: a per-seat monthly access price, an included allowance of premium requests per user per month, and a marginal charge of \$0.04 for each premium request beyond the allowance.\footnote{Tiered premium-request allowances documented at: \url{https://docs.github.com/en/copilot/get-started/plans}} The structure is uniform across the Student plan (300 included premium requests per month), the Pro plan (300), the Pro+ plan (1{,}500), the Business plan (300 per user), and the Enterprise plan (1{,}000 per user). Each supported model is associated with a premium-request multiplier that determines how many premium requests a single model interaction deducts from the allowance: a $1{\times}$ model consumes one premium request per interaction, while advanced reasoning or fast-mode models apply higher multipliers (for example, $3{\times}$ or $30{\times}$). A framework that consumes fewer premium requests to complete the same task therefore consumes a smaller share of the buyer's monthly allowance. Economic research on three-part tariff choice shows that buyer preference for this pricing structure is driven by demand uncertainty rather than marginal price alone, with consumers steering toward allowance-based plans to hedge against bill variance \citep{lambrechtseimskiera2007, liandkumar2022}.

The primary cost metric for the study is \textbf{premium requests per session}: the total number of premium requests consumed across all conversations of a single framework session. Each participant contributes one APM-session count and one Spec-kit-session count for the same task, aggregated and compared across the cohort. This metric maps directly onto the buyer's budget exposure under the subscription plans described above. The metric is deliberately decoupled from the task rubric: request counts are compared between frameworks for the same completed work, without attempting to attribute requests to individual rubric points or features.

The secondary cost metric is a phase-broken breakdown of the per-session request count. For APM, the planning phase corresponds to the Planner conversation and the implementation phase to the Manager and Worker conversations, a boundary marked naturally by the conversation identity in the chat export. For Spec-kit, the planning phase covers all requests up to and including the last \texttt{/speckit.tasks} invocation, together with any preceding commands in the planning cluster: \texttt{/speckit.constitution}, \texttt{/speckit.specify}, \texttt{/speckit.plan}, \texttt{/speckit.clarify}, \texttt{/speckit.analyze}, and \texttt{/speckit.checklist}. The implementation phase covers all requests from \texttt{/speckit.implement} onward. The phase split locates where each framework spends its budget and exposes the source of any observed cost differential between frameworks.

All sessions use a single underlying model, held fixed across both frameworks and across both sessions of each participant: GPT-5.4. This is a $1{\times}$ premium-request model, available to participants on the Student plan as well as the Pro, Pro+, Business, and Enterprise tiers.\footnote{Model multiplier values and plan availability documented at: \url{https://docs.github.com/en/copilot/reference/ai-models/supported-models}} Holding the model fixed at a uniform $1{\times}$ multiplier eliminates multiplier-induced variance in the cost metric, so that a difference in premium-request counts reflects a difference in framework behavior rather than a difference in model choice.

The study does not measure raw inference cost in terms of tokens consumed or dollar-equivalent API pricing. Recent empirical work on the LLM market documents that the raw inference price of a comparably capable model has declined by roughly three orders of magnitude over the preceding two years, and that the same model hosted by competing providers can differ in price by as much as 90\% \citep{demireretal2025}. A subscription buyer is insulated from both the deflationary curve and the cross-provider heterogeneity: the cost paid per month is fixed by the plan, and the cost paid per request is set by the vendor's multiplier table rather than by inference economics. Measuring dollar-equivalent token cost would therefore reflect a quantity that neither framework's user actually incurs. GitHub Actions minutes consumed by Copilot cloud agents are also out of scope: neither APM nor Spec-kit invokes the cloud agent feature in the testbed task, so the dual-consumption mechanism documented for cloud agents does not apply.\footnote{Dual consumption of premium requests and Actions minutes by Copilot cloud agents documented at: \url{https://docs.github.com/en/billing/concepts/product-billing/github-copilot-premium-requests}}

\subsubsection{Reliability Metrics}

The reliability metrics capture how autonomously each framework executes work once a task has been delegated to an AI agent. Prior empirical work has shown that the acceptance rate of AI-generated output is one of the strongest observable predictors of perceived productivity \citep{ziegleretal2024}, and that acceptance rates in field settings can fall below 44\% for experienced developers working on mature codebases \citep{beckeretal2025}. When suggestions are accepted but later modified, the modification itself reflects a reliability gap: the agent produced output close enough to be useful but not correct enough to be used as is. The metrics below operationalize these reliability signals directly from the tool-call and code-modification events in the Copilot chat export.

The \textbf{tool success rate} is the proportion of agent tool invocations that return a non-error result. The \textbf{tool retry rate} is the proportion of tool invocations followed by a repeated call to the same tool with adjusted arguments within the same agent turn, indicating that the first attempt failed or was rejected. The \textbf{user edit rate on terminal commands} is the proportion of terminal-execution tool calls whose command string was modified by the user before execution rather than executed verbatim, indicating a lack of trust in the agent's generated command. Together these metrics capture the frequency with which agents produce directly usable output rather than output requiring re-attempts or human correction.

\subsubsection{Process Metrics}

The process-efficiency metrics capture the human coordination burden each framework imposes across a session. Developer productivity is conventionally measured along the SPACE dimensions: satisfaction, performance, activity, communication, and efficiency. Recent empirical work has documented that AI coding assistants shift the allocation of developer time toward review and prompting activities rather than active coding \citep{ziegleretal2024, beckeretal2025}. \citet{beckeretal2025} measured that developers allowed to use AI tools spent 9\% of their time reviewing AI output, 8\% prompting, and 4\% waiting, while accepting fewer than 44\% of generated suggestions. The metrics below operationalize the user's coordination effort in a form extractable directly from the Copilot chat exports.

The primary process metrics characterize the distribution and magnitude of user inputs during a session. Each user message is assigned to one of three buckets: short (brief acknowledgments or routing messages), protocol (framework-protocol messages such as APM handoff routing or Spec-kit slash-command invocations), and standard (substantive task-related prompts). The \textbf{behavior distribution} reports the share of each bucket in the session's total user-message count. The \textbf{behavior magnitude} reports the average character count per bucket. Together these views expose whether a framework's user burden is concentrated in mechanical message-shuttling (high protocol share, low magnitude) or in substantive problem-solving (high standard share, high magnitude).

\textbf{Session duration} is measured as the wall-clock time from the first user message of the session to the last assistant message. For APM, this spans all of the Planner, Manager, and Worker conversations belonging to the session. For Spec-kit, this is the span of the single conversation from session start to completion.

The shape of this metric set follows the verification-burden pattern documented in enterprise-scale AI coding studies \citep{paradisetal2024, cuietal2025}. In those settings, developers with heavier daily coding practice extracted disproportionately larger speed benefits from AI assistance, consistent with the hypothesis that verifying generated output imposes a cognitive cost that scales with prompt complexity. A framework that keeps user inputs short and protocol-routed trades substantive prompt engineering for higher-volume mechanical coordination. A framework that pushes the user toward long substantive prompts makes the opposite trade, requiring more per-prompt engineering effort in return for fewer coordinating interactions \citep{vukovicetal2026}.

\subsubsection{Functional Metrics}

The functional dimension is evaluated against the 100-point grading rubric introduced in Section~\ref{sec:grading}. Final code artifacts (\texttt{.patch} files) are scored across three dimensions:

\begin{itemize}
    \item Baseline Regression: ensures that existing functionality (12 points) remains intact after the patch is applied, isolating the framework's impact on code stability.
    \item Functional Correctness: end-to-end validation of the new Python features (36 points) and the complete C replica (52 points) against the specification.
    \item Robustness: edge-case handling including authentication failures, invalid inputs, empty responses, and memory safety (Valgrind validation for the C implementation).
\end{itemize}

This three-dimensional scoring captures partial credit across baseline preservation, feature-level correctness, and robustness, rather than collapsing task completion into a single binary outcome of the kind commonly used in prior empirical work on AI coding assistants \citep{cuietal2025, pengetal2023, paradisetal2024}.

\section{Results}
\label{sec:results}

\subsection{Functional Performance Analysis}

Primary metrics: total score distribution, completion rates (100/100, 49--99, 12--48, baseline-only), baseline regression rates, and feature implementation success rates for Python and C.

Category analysis: success rates per test category (build, protocol, login, logout, courses, authstatus, announcements) for both Python and C implementations, identifying framework-specific failure patterns.

Comparative analysis: paired t-tests comparing APM and Spec-kit for total score, category scores, and completion rates. Each test is accompanied by a standardized effect-size estimate, Cohen's $d$, which expresses the mean difference between two groups in pooled-standard-deviation units and distinguishes statistical significance from practical significance.

\subsection{Economic and Process Efficiency Analysis}

Economic and process metrics defined in Section~\ref{sec:metrics} are compared between frameworks on a per-participant paired basis. For the primary cost metric (premium requests per session), paired t-tests compare the APM and Spec-kit distributions across the cohort, with Cohen's $d$ reported alongside each test to quantify effect size. The phase-broken secondary cost metric is reported as the mean share of planning-phase versus implementation-phase requests per framework.

For process metrics, behavior distribution and behavior magnitude are reported by input bucket for each framework. Per-bucket paired t-tests are applied to the participant-level differences across the short, protocol, and standard buckets. Session duration is compared using the same paired t-test approach.

Correlation analysis relates the cost and process metrics to the functional rubric score. Pearson correlation coefficients are reported for premium-requests-per-session against total rubric score, and for session duration against rubric score, both within each framework and across the combined cohort. These correlations surface whether framework-induced variation in cost or process burden translates into functional outcomes.

\subsection{Learning Effects and Confounding}

Participants complete the same task twice (Session 1 and Session 2) using different frameworks. This creates a learning effect where task familiarity from S1 influences S2 performance, potentially confounding framework comparisons.

Analysis strategy:

\begin{itemize}
    \item Learning Effect Matrix: calculate mean improvement from S1 to S2 for both framework orderings across all metrics (functional scores, cost, process efficiency).
    \item Order Effect: compare APM-first vs.\ Spec-kit-first directions to test whether order of framework exposure affects learning.
    \item Baseline Learning: overall mean improvement across both directions (pure task learning effect regardless of framework).
\end{itemize}

Key questions: does task learning confound framework comparisons? Is there a preferred first framework that maximizes S2 improvement? How should learning effects be controlled for when comparing frameworks?

\subsection{Threats to Validity}

This subsection enumerates internal, external, and construct validity threats and the mitigations applied.

\subsubsection{Internal Validity}

\textbf{Learning effects from the within-subjects design.} Each participant completes the same task twice, and task familiarity from the first session can influence performance in the second. Counterbalancing the framework order across participants mitigates the framework-effect confound but does not eliminate the underlying learning curve. The Learning Effects analysis in Section~\ref{sec:results} quantifies the mean improvement between sessions across both orderings and is the primary defence against this threat.

\textbf{Participant experience heterogeneity.} Productivity and process-efficiency effects of AI coding assistants vary with developer experience and daily coding volume \citep{pengetal2023, ziegleretal2024, paradisetal2024}. The within-subjects design partially absorbs cross-participant variance by pairing each participant with themselves, but residual dispersion may limit the precision of cohort-level estimates.

\textbf{Self-reported versus observed measures.} Subjective developer-reported productivity often diverges from objective time-in-motion measurements, occasionally in the opposite direction \citep{beckeretal2025, pengetal2023}. This study reports only instrumented, export-derived metrics and does not combine them with self-reports, which limits the process-efficiency findings to measurable coordination activity rather than subjective effort or satisfaction.

\subsubsection{External Validity}

\textbf{Single-vendor, single-model evaluation.} The case study is run exclusively on GitHub Copilot with a fixed $1{\times}$ multiplier model. Empirical enterprise data shows that most API workloads concentrate on a single model even when multi-homing is available, with more than 90\% of volume typically routed to a single chosen model \citep{demireretal2025}. The design therefore reflects empirical adoption patterns, but the findings do not generalise to settings where frameworks dynamically route between models.

\textbf{Task complexity and domain specificity.} The testbed task is a complex software engineering assignment requiring two-language implementation and legacy-codebase research. In an empirical analysis of twelve commercial LLM use-case categories, \citet{demireretal2025} report that programming commands both the highest average intelligence index and the highest willingness to pay among buyers. The chosen testbed is therefore representative of the domain most sensitive to marginal AI capability, but not of administrative, analytical, or creative workflows.

\textbf{Lab-to-field generalisation gap.} Lab-style productivity measurements for AI coding assistants have exceeded enterprise field measurements by more than a factor of two, and experienced developers on mature codebases have been observed to be slower with AI than without \citep{pengetal2023, cuietal2025, beckeretal2025}. The case study is positioned between lab and field conditions, and its measurements are neither pure laboratory benchmarks nor natural-setting observations.

\textbf{Temporal decay of findings.} The AI coding assistant field is evolving rapidly. Specific effect sizes are tied to the model version, the Copilot pricing parameters, and the framework releases available during the participant window. The three-part tariff allowance sizes and model multipliers are subject to vendor change, and cost-efficiency findings are defensible against current pricing but may require re-estimation under materially different parameters \citep{lambrechtseimskiera2007}.

\subsubsection{Construct Validity}

\textbf{Cost measured within a single procurement model.} The cost metric measures share of the monthly premium-request allowance consumed within the subscription-plus-quota procurement model. It does not measure dollar-equivalent inference cost, which is decoupled from the subscription price and has declined by roughly three orders of magnitude over the preceding two years \citep{demireretal2025}. The subscription buyer is by definition insulated from that translation, so the scoping is intentional rather than a defect.

\textbf{Behavioral input buckets as process-efficiency proxy.} The short, protocol, and standard input buckets are defined for this study and extracted from the chat-export content. They are not validated against an external coordination-burden instrument such as the SPACE framework \citep{ziegleretal2024} or the NASA Task Load Index. Their validity as proxies for human coordination effort rests on face validity alone: the relative ordering of frameworks along these metrics is robust, but the absolute magnitude of differences is interpretive rather than calibrated.

\textbf{Binary functional outcomes.} The 100-point rubric captures correctness and robustness but not code quality, maintainability, security posture, or long-term technical debt. Prior empirical work on AI coding assistants has consistently noted that code-quality dimensions are not captured by pass/fail functional measurement \citep{paradisetal2024, cuietal2025}, and this study inherits that limitation.

\textbf{Chat-export data scope.} Metric extraction is limited to the per-conversation JSON exports produced from the VS Code Command Palette. Inline code-completion events that do not appear in the chat export are invisible to the metric set. The reliability and process metrics therefore characterise only the agent-driven portion of the workflow rather than the full IDE interaction.
