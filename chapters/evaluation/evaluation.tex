\section{Methodology and Research Questions}
\label{sec:methodology}

We evaluate the Agentic Project Management (APM) framework in a realistic setting through a comparative case study with human participants. The study compares APM, the framework presented in Chapter~\ref{chap:framework-design} that coordinates several agents through the user, against GitHub Spec-kit, a framework applying the spec-driven discipline of Chapter~\ref{chap:background} through one agent. The study was conducted on the Claude Code command-line interface, which both frameworks operate on top of, over a study window from 5 May to 5 June 2026; pricing, model, and command-set statements in this chapter refer to that window.

Both frameworks build on the spec-driven discipline of Section~\ref{sec:spec-driven-development}, approaching the task through explicit specification and planning, and each realises it in its own way. The most salient difference, and the one this comparison turns on, is whether one agent carries the workflow or several agents who coordinated through the user. The evaluation probes that difference along four dimensions, defining the following Research Questions (RQs):

\begin{itemize}
    \item \textbf{RQ1 (Economic):} How does APM's user-mediated coordination between several agents affect the dollar cost of completing a task relative to Spec-kit's workflow carried by one agent, and is that difference consistent across models of differing capability?
    \item \textbf{RQ2 (Process):} How does APM's user-mediated coordination between several agents change the time a task takes and the effort it demands of the user, relative to Spec-kit's workflow carried by one agent?
    \item \textbf{RQ3 (Functional):} How do the two frameworks differ in functional outcome, in how much of the task each completes and in how they fail when they fall short?
    \item \textbf{RQ4 (Perception):} How does participants' self-reported experience of each framework relate to the behaviour measured from their sessions?
\end{itemize}

\section{Spec-kit, the Comparison Framework}
\label{sec:comparison-framework}

The comparison sets APM against GitHub Spec-kit, two open-source frameworks that apply the spec-driven discipline of Section~\ref{sec:spec-driven-development} on top of an existing coding agent. APM's design is described in full in Chapter~\ref{chap:framework-design}; Spec-kit, the comparison framework, is introduced here so the two can be read on the same terms.

Spec-kit\footnote{Documentation available at: \url{https://github.github.io/spec-kit/}} is GitHub's open-source spec-driven development toolkit. One agent applies the discipline from end to end, producing the specification and the plan and then implementing them, all within one continuous conversation. That agent may still launch subagents through the underlying coding agent, just as APM's agents can.

The work is driven by a set of slash commands that the developer triggers, or the agent autonomously invokes, each a bundle of instructions that walks the agent through one step of the workflow. The first is \texttt{/speckit-constitution}, which fixes the project's governing principles in a file; these come either from the user or from the agent's reading of the existing project, and the agent is to uphold them throughout. The specification is then built through three sequential commands:

\begin{enumerate}
    \item \texttt{/speckit-specify}: directs the agent to produce a structured specification of requirements, user stories, and acceptance criteria from a feature description.
    \item \texttt{/speckit-plan}: has it turn that specification into a technical implementation plan with architecture decisions, data models, and API contracts.
    \item \texttt{/speckit-tasks}: prompts it to derive an executable task list from the plan, annotated with dependencies and sequencing constraints.
\end{enumerate}

Finally, \texttt{/speckit-implement} has the agent work through the task list in sequence, while further commands support iterative refinement, cross-artifact consistency checking, and custom quality checklists along the way.

Across these steps the workflow is command-driven, and within each step the agent works largely on its own. It fills gaps in the brief with documented assumptions and puts a question to the developer only where an ambiguity would change the scope of the work.

\section{Case-Study Design}
\label{sec:case-study-design}

The study is a within-subjects comparative case study across a homogeneous cohort of twelve participants drawn from university students and working professionals. Every participant completes the same task twice, once with each framework, so per-participant variance in skill, prior experience, and working style is absorbed into each pairwise comparison rather than confounding it. The cohort therefore yields twenty-four sessions in total.

Each participant receives a package containing the task brief, the materials to set up a testing environment, and a guide that walks them through that setup and the session. The brief and the environment are detailed in the two subsections that follow, and the package, with the rest of the study's software and data, is listed in Appendix~\ref{app:availability}.

\subsection{Task Specification}
\label{sec:task-spec}

The task is delivered to each participant as a complete product requirements document (PRD), in the form a developer receives a real feature brief. It builds on \texttt{eclass-mcp-server},\footnote{Repository available at: \url{https://github.com/sdi2200262/eclass-mcp-server}} an existing open-source Python Model Context Protocol (MCP)\footnote{Protocol specification available at: \url{https://modelcontextprotocol.io}} server that connects to Open eClass,\footnote{Repository available at: \url{https://github.com/gunet/openeclass}} the learning-management platform used across Greek universities. Participants extend the server with two new announcement-retrieval tools, then reimplement it in full, including those tools, as a standalone native C replica under strict constraints.

The work is deliberately broad. Building the new tools requires investigating the unfamiliar legacy PHP codebase behind Open eClass, to learn how it exposes its data, and implementing them in Python. The C replica reproduces the entire server from scratch as a standalone, drop-in microservice, covering not just the tool logic but the protocol layer that the Python server gets from the MCP SDK. The task additionally constrains how the replica is built, requiring that protocol layer to be implemented by hand, without a JSON-parsing library, and the binary to satisfy a verifiable memory-safety standard. Spanning a legacy system and two implementation languages, the task sets both frameworks a piece of demanding, end-to-end engineering workload.

\subsection{Task Environment}
\label{sec:task-env}

Following the guide, each participant sets up a fresh, dedicated Linux virtual machine, so all their work happens in the same isolated environment. The machine provides the development toolchain the task needs and a workspace holding the PRD, a clone of \texttt{eclass-mcp-server} at a fixed baseline against which the participant works, and a clone of the Open eClass codebase the agent can investigate. A containerised Open eClass instance, built from that same fixed version of the platform and seeded with a fixed set of mock data, runs in the background throughout the session, alongside a mock single-sign-on service. The participant and the agent can therefore validate their work against the running platform. Every participant develops against the same fixed state, and the submitted solution is later assessed against an equivalent environment.

\subsection{Sessions and Data}
\label{sec:sessions-data}

Each of a participant's two sessions is time-boxed to a maximum of three hours, within which the participant carries out the task with the assigned framework and then answers a short post-session questionnaire. Between the two sessions the environment is reset to its initial baseline, so that no code, workspace state, or assistant context from the first session carries into the second.

Two factors are counterbalanced across the cohort: the framework order and the model assignment. The framework-order factor varies which framework a participant encounters first; counterbalancing it lets any first-to-second-session improvement, a learning effect from growing task familiarity, be distinguished from the framework's own effect. The model factor holds one Claude model fixed across both of a participant's sessions. Each participant is assigned either Claude Opus 4.7 or Claude Sonnet 4.6, the two models Claude Code offered during the study window, which differ in capability. Crossing the two factors gives four assignment cells of three participants each.\footnote{One participant deviated from their assigned order at run time: a tooling failure ended their first Spec-kit attempt before any task work was completed, they ran APM the following day, and then repeated Spec-kit. The realized counterbalance is therefore 3/4/3/2 across the four cells and the Sonnet group has 4 APM-first and 2 APM-second rather than 3 and 3 instead of the intended 3/3/3/3. All order-split tables in Appendix~\ref{app:cost-breakdowns} and Appendix~\ref{app:process-breakdowns} classify participants by realized execution order throughout.}

From each session we collect a participant submission of three parts: the solution patch the participant writes against the baseline, the session transcripts the command-line interface records for every conversation opened, and the participant's response to the questionnaire.

\section{Measures}
\label{sec:measures}

Every measurement defined in this section is extracted from a participant's submission by the same procedure across the cohort. The economic and process measurements are computed from the session transcripts by a parser. The functional measurements are computed from the solution patch by an automated grader, against a fixed scoring rubric. The self-reported perception measurements come from the post-session questionnaire. The parser and grader are part of the evaluation infrastructure listed in Appendix~\ref{app:availability}.

Each transcript-derived measurement is computed at more than one scope, a scope being the portion of a session it is aggregated over. The session scope is the whole session, the headline on which the two frameworks are compared, since it puts APM's multi-conversation workflow and Spec-kit's single conversation on the same denominator. The phase scope splits the session into its planning and implementation portions and shows how each measurement divides between them. The role scope applies to APM alone, since Spec-kit has no agent roles to separate, and is a descriptive, deeper look at how each measurement is spread across its agents. Both the phase split and, for APM, the role attribution follow the frameworks' own workflow as recorded in the transcript, rather than an arbitrary division of the session. The functional dimension admits no such split and is reported at the session scope alone.

\subsection{Economic}
\label{sec:measures-economic}

The economic measurement is the \textbf{dollar-equivalent cost}, computed by pricing every call recorded in the session's transcripts against Anthropic's published per-token rate card in effect during the study window, recorded in Appendix~\ref{app:rate-card}. Calls made by the conversation's main agent are priced at that conversation's declared model; calls made by subagents are priced against the model recorded in the platform's sibling subagent transcript for that dispatch. The cost is measured at the session scope and broken down further to locate where the spending accrues, by token category, across the planning and implementation phases, and for APM across its agent roles.

\subsection{Process}
\label{sec:measures-process}

The process measures capture two aspects of a session, its temporal shape and its interaction shape. The first is how the session's time was spent; the second is how the user engaged with the agent, which reflects the effort each framework demands.

The temporal shape of the session is captured by the session duration and the two measures that decompose the time within it, the turn time and the inter-turn time, all reported at session and phase scope only:
\begin{itemize}
    \item \textbf{Session duration} is the wall-clock span from the first user message of the session to the last assistant message, bounded above by the three-hour cap.
    \item \textbf{Turn time} is the time an agent was actively working, the wall-clock union of every turn's interval. It is reported in total and split into the time only one agent was working (\textbf{solo}) and the time two or more were working at once (\textbf{concurrent}). For APM this surfaces whether the participant's agents worked in parallel or serially.
    \item \textbf{Inter-turn time} is the residual of the session duration once turn time is subtracted. It is the assistant's idle time as recorded in the transcripts, not read as a measure of participant activity, since a gap may be spent reading, thinking, or away from the task.
\end{itemize}

The interaction shape is captured by the count of turn prompts, the number of turns the user opened across the session, the counts of delivered and attempted steers, and two views of how those messages divide by content. A user message is one of two kinds:
\begin{itemize}
    \item A \textbf{turn prompt} is a message submitted while the agent is idle, opening a new turn that runs to the agent's idle return.
    \item A \textbf{steer} is an interjection enqueued while the agent is still working, which the platform either delivers during the turn or abandons if the user retracts it first.
\end{itemize}
The two steer counts separate intent from effect. Every steer the participant began to send is an attempted steer; a delivered steer is one the platform actually passed to the working agent. A steer abandoned before delivery carries no content the agent acted on, so it is counted but not bucketed below, and the gap between the two counts records the interjections a participant started and then withdrew.

Each turn prompt and delivered steer also falls into a content bucket, by whether it invokes a framework command and, otherwise, by its length:
\begin{itemize}
    \item \textbf{Protocol} for an APM or Spec-kit framework command.
    \item \textbf{Short} for a brief non-command message below a length threshold.
    \item \textbf{Standard} for a longer, substantive message at or above it, such as a correction, a decision, or guidance.
\end{itemize}
The two bucket views summarise how the messages fall across the buckets. The \textbf{bucket-share distribution} is each bucket's share of the messages, counted for prompts and delivered steers separately and together. The \textbf{magnitude per bucket} is the mean character count of the messages in each bucket, taken for the turn prompts and the delivered steers separately. Together these distinguish effort spent shuttling mechanical messages, where the protocol share is high and the magnitude low, from effort spent on substantive correction and guidance, where the standard share and magnitude are high.

Unlike the temporal measures, the interaction counts and both bucket views are also reported at role scope for APM, attributing each turn prompt and delivered steer to the agent the participant was addressing. This shows how the user interacted with each of the framework's roles.

\subsection{Functional}
\label{sec:measures-functional}

The functional dimension is scored by an automated grader that runs a fixed rubric of behavioural assertions against each submission. The grader observes only the running server's responses and the compiled C binary, never the participant's source, so it is indifferent to how the solution is built. It runs each submission against an equivalent environment, the same platform seeded afresh to exercise the behaviours under test. The rubric is a fixed set of ninety atomic checks, each testing one expected behaviour and carrying a calibrated point weight toward a 100-point total.

Each check returns one of three verdicts. A \textbf{passed} check matches an accepted form and earns its full points. A \textbf{partial} check matches none but lands near one, earning its points scaled by its similarity to the nearest form and flagged for review. A \textbf{failed} check earns zero. The functional outcome is the \textbf{total score}, the points earned across the rubric, which separates into a strict part, the full points of the passed checks, and a partial part, the fractional credit of the near-misses. A second grading run with a compact input serialization is reported as a diagnostic in Section~\ref{sec:disc-grading-blackbox}. It is not part of the framework comparison, which uses the total score.

The 100 points split across the task's two parts, 30 on the Python extension and 70 on the heavier C replica. The \textbf{per-section scores} decompose the total across these two parts, locating where each framework's work lands.

\subsection{Perception}
\label{sec:measures-perception}

The perception measures come from a short questionnaire answered at the end of each session, the self-reported counterpart to the measured behaviour. Its core is \textbf{eight rating items} on a one-to-five ordinal scale, each answered once per session and paired by framework. The items cover the participant's prior familiarity with the framework, confidence in the submitted solution, the framework's perceived effectiveness, the session's mental demand and frustration, the overall effort invested, and the effort spent checking and steering the AI. The items differ in polarity, a higher rating being the better outcome for some, such as confidence and effectiveness, and the worse for others, such as mental demand, frustration, and the three effort items.

Beyond the rating items, the questionnaire asks one second-session question on a five-point scale, whether the task felt easier or harder than with the first framework. It records the participant's own completion state against the three-hour cap. It closes with two free-text prompts, read only as illustration, on what stood out and any closing remarks. The full instrument is reproduced in Appendix~\ref{app:questionnaire}.

\section{Analysis Plan}
\label{sec:analysis-plan}

The cohort is small: in total, data from twelve participants, thinned to six against six when split by model. The analysis therefore leads with the measured values and with summaries of the per-participant difference between a participant's two sessions. Three such summaries are common to every measure and are set out here before being applied to each in turn: the direction of the framework effect, its typical size, and the uncertainty around that size.

Every comparison is made within participant. For a given measure, participant~$i$ contributes the paired difference $d_i = x_i^{\text{APM}} - x_i^{\text{SK}}$, the value from their APM session minus the value from their Spec-kit session. The analysis works from these $n$ paired differences, with $n = 12$ for the full cohort.

The direction is the sign count, the tally of participants whose difference favours APM against the number favouring Spec-kit. Where the tally is one-sided we test it with the sign test~\cite{hollander2014nonparametric}. Its statistic $B$ is the number of positive differences,
\[
    B = \sum_{i \,:\, d_i \neq 0} \mathbf{1}\!\left( d_i > 0 \right).
\]
Tied pairs, where a participant's two sessions come out equal, give no direction and are set aside, reducing $n$ to the count of non-zero differences. If neither framework were systematically higher, $B$ would behave like the number of heads in $n$ fair coin tosses, and the test reports how improbable the observed tally, or a more one-sided one, would be under that even-odds model.

The typical size of the difference is estimated two ways. The first is the median of the differences, the middle value once they are ordered. The second is the Hodges-Lehmann estimate~\cite{hodges1963location}, the median of the averages of every pair of differences,
\[
    \hat{\theta} = \operatorname{median}\left\{ \frac{d_i + d_j}{2} \;:\; 1 \le i \le j \le n \right\}.
\]
It summarises the differences through all their pairwise averages rather than the single middle value, so it shifts in finer, steadier steps while keeping the same resistance to extreme values where they occur. The mean is reported beside both, where a divergence from the median marks an asymmetric spread of the differences.

The uncertainty around that typical difference is a confidence interval for it, built from the Wilcoxon signed-rank statistic~\cite{wilcoxon1945signedrank, hodges1963location}. Unlike the sign count, this statistic uses the sizes of the differences and not only their direction, ranking them by absolute size and summing the ranks of the positive ones,
\[
    W^{+} = \sum_{i \,:\, d_i > 0} \operatorname{rank}\!\left( |d_i| \right).
\]
The interval's coverage depends on the number of pairs, and is 95.8\% across the full cohort of twelve and 96.9\% across the six-participant model splits.

The economic and process measures are continuous, and each is reported both by each framework's measured values and by the within-participant paired difference between them, taking the three summaries in full. Where a measure has no counterpart to pair against, as with APM's per-role attribution, or is a composition whose shares move together rather than a single magnitude, no paired difference is formed. Such a measure is reported descriptively by each framework's central values alone, the median, Hodges-Lehmann estimate, and mean, without the sign test or the confidence interval. At this cohort size, distinct session-level edge cases can shift individual summaries; where that happens, the affected table row notes the case. The functional total score is compared within participant the same way. Because that score is bounded by the rubric's hundred-point ceiling, its comparison leads on the sign count and the spread of the differences, with the typical-size estimate in support.

The perception ratings are ordinal, so each item is summarised by order-based statistics. These are its sign count and the median of its paired differences, read with the item's polarity, with the per-framework median ratings giving a profile across the items. Each rating is also read against the behaviour it should reflect, descriptively at this cohort size, as the pattern of agreement and divergence between the two.
