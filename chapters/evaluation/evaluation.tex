\section{Evaluation Methodology}
\label{sec:evaluation}

This chapter details the methodology used to evaluate the Agentic Project Management (APM) framework. To assess the framework in a realistic setting, we conducted a comparative case study involving human participants. The study compares APM, a multi-agent framework that distributes work across specialized agents, against GitHub Spec-kit, a single-agent toolkit that guides one AI agent through a structured specification-driven workflow. Both frameworks are described in Section~\ref{sec:frameworks}. The case study was conducted in May 2026; all Copilot platform, pricing, and model-availability statements in this chapter refer to that snapshot.

The evaluation measures three distinct dimensions:

\begin{itemize}
    \item Economic Efficiency (share of the Copilot monthly request allowance consumed per session)
    \item Process Efficiency (human cognitive load and interaction burden)
    \item Functional Efficacy (ability to complete non-trivial tasks)
\end{itemize}

\subsection{Research Objectives}

The primary objective of this research is to determine whether the structural overhead introduced by APM (i.e., the Planning and Implementation phases) produces measurable improvements over a single-agent workflow. Prior empirical work on AI coding assistants has concentrated on productivity and task-completion time \citep{pengetal2023, cuietal2025, paradisetal2024, ziegleretal2024, vukovicetal2026}, with comparatively little systematic treatment of cost under the subscription-based procurement model through which Copilot is predominantly adopted. This evaluation contributes a cost perspective alongside the process and functional dimensions.

We define the following Research Questions (RQs):

\begin{itemize}
    \item \textbf{RQ1 (Economic Efficiency):}
    \begin{itemize}
        \item Under GitHub Copilot's subscription-plus-quota pricing structure, does APM's multi-agent coordination consume fewer premium requests per session than Spec-kit's single-agent workflow?
        \item If a difference in request consumption is observed, is it large enough to meaningfully shift the share of a buyer's monthly allowance burned per task completion?
        \item Where in each framework's workflow (planning phase versus implementation phase) does request consumption concentrate, and does that concentration pattern differ between frameworks?
    \end{itemize}
    \item \textbf{RQ2 (Process Efficiency):}
    \begin{itemize}
        \item Does the structured coordination of APM reduce the amount of manual effort the user must invest during execution, particularly interventions, corrections, and clarifications?
        \item If a difference in user effort is observed, is it significant enough to justify the structural overhead APM introduces?
        \item Given that the User remains in the loop as a message carrier, can the agents coordinate effectively enough that the User's role stays limited to shuttling messages rather than correcting or redirecting agent behavior?
    \end{itemize}
    \item \textbf{RQ3 (Functional Efficacy):}
    \begin{itemize}
        \item Can APM successfully deliver complex, non-trivial features in scenarios where single-agent workflows are prone to failure due to context exhaustion, loss of coherence across long sessions, or inability to coordinate work across multiple concerns?
        \item How does the performance of APM compare to the performance of a single-agent workflow?
    \end{itemize}
\end{itemize}

\subsection{Frameworks Under Evaluation}
\label{sec:frameworks}

The two frameworks are both open-source and spec-driven, running on the same AI IDE platform. Both structure work through explicit specification and planning artifacts before implementation begins. They differ in how execution is organized: Spec-kit operates within a single agent conversation, while APM distributes work across multiple specialized agents.

\subsubsection{GitHub Spec-kit}

Spec-kit\footnote{Documentation available at: \url{https://github.github.com/spec-kit/}} is a specification-driven development toolkit developed by GitHub. It guides a single AI agent through a structured workflow using three sequential commands:

\begin{enumerate}
    \item \texttt{/speckit.specify}: transforms a feature description into a structured specification containing requirements, user stories, and acceptance criteria.
    \item \texttt{/speckit.plan}: converts the specification into a technical implementation plan with architecture decisions, data models, API contracts, and supporting documents.
    \item \texttt{/speckit.tasks}: derives an executable task list (\texttt{tasks.md}) from the plan, with parallelism annotations and sequencing constraints.
\end{enumerate}

Execution is triggered by a fourth command, \texttt{/speckit.implement}, which parses the task list and carries out each task in sequence. Additional commands support iterative refinement (\texttt{/speckit.clarify}), cross-artifact consistency checking (\texttt{/speckit.analyze}), and custom quality checklists (\texttt{/speckit.checklist}). A constitution mechanism, maintained via the \texttt{/speckit.constitution} command, allows users to establish architectural rules that the agent enforces throughout the workflow.

All planning and implementation happens within one continuous conversation. The agent acts as both planner and executor, and the full specification, plan, and task context accumulates in a single context window. Spec-kit produces a fixed set of artifact types (specification, plan, data model, contracts, research, tasks) regardless of project type; the templates are predefined and every project receives the same artifact layout.

\subsubsection{APM in Comparison}

Where Spec-kit runs the entire workflow in a single conversation, APM (described in detail in the preceding chapters) separates planning, coordination, and execution across three agent roles, each operating in its own conversation with scoped context. Agents communicate through a file-based Message Bus rather than a shared context window; planning documents adapt to each project rather than conforming to a predetermined artifact layout; and the user acts as a message carrier between conversations. When an agent's context fills, a Handoff mechanism preserves working knowledge across context boundaries.

\subsection{Testbed and Task Design}

To evaluate the frameworks under realistic constraints, we utilized an existing open-source project, the \texttt{eclass-mcp-server},\footnote{Repository available at: \url{https://github.com/sdi2200262/eclass-mcp-server}} a Python-based Model Context Protocol (MCP)\footnote{Protocol specification available at: \url{https://modelcontextprotocol.io}} server designed to interface with the \texttt{openeclass} platform.\footnote{Repository available at: \url{https://github.com/gunet/openeclass}} Openeclass is an online platform for Greek universities that allows students to manage their courses and assignments. The case study's own material is organized across two repositories, a public task repository and a restricted-access dataset repository for submitted participant data; both are documented in the evaluation appendix.

\subsubsection{Task Description}

The task requires participants to implement two new announcement tools in the Python MCP server and to create a complete native C replica of the entire server.\footnote{\raggedright Task specification and grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task}} The two tools are:

\begin{itemize}
    \item \texttt{get\_course\_announcements}: retrieves announcements for a specific course.
    \item \texttt{get\_general\_announcements}: aggregates system-wide and per-course announcements.
\end{itemize}

The C implementation adds significant complexity: participants must manage code translation, memory safety, and protocol details across two different languages. This combination of feature implementation and full-language replication is designed to challenge the limits of agent coordination and expose any differences between the two frameworks, especially when context management becomes a bottleneck.

Key technical challenges:

\begin{enumerate}
    \item Dynamic Data Source: the data required for the new features is not served as static HTML. Agents must research the legacy codebase to discover a specific AJAX endpoint and its behavior.
    \item Response Post-Processing: the endpoint returns JSON whose payload is an array of raw HTML strings, so agents must add a second layer of parsing to extract each record; the legacy API also offers no server-side date filtering, so agents must parse and filter locale-formatted dates client-side.
    \item C Implementation: agents must build a native C MCP server replica, manually implementing JSON-RPC 2.0 with standard C string manipulation (no external JSON libraries such as cJSON or Jansson). Use of \texttt{libcurl} for HTTP/HTTPS and \texttt{libxml2} for HTML parsing was required. A working Makefile must build the C binary.
\end{enumerate}

\subsubsection{Grading}
\label{sec:grading}

Submissions are evaluated by an automated black-box test suite that applies each participant's patch against fixed baseline commits of the upstream repositories and runs a comprehensive test battery.\footnote{Grading infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task/tree/main/grader}} The test suite awards 100 points total: 12 points for baseline functionality (existing Python tools), 36 points for the two new Python features (18 points each), and 52 points for the C replica implementation. A submission with no patch applied receives the baseline score of 12/100 points.

The grader runs these tests against a Docker-based replica of the openeclass platform rather than against the live University instance that participants develop against. Baseline commits, the replica environment, the multi-stage grading pipeline, and the test-suite composition are documented in the evaluation appendix.

\subsection{Study Design}

The study is conducted on a single AI IDE platform, VS Code with GitHub Copilot, and compares the two frameworks across a homogeneous cohort of participants. It is designed as a within-subjects experiment, so that each participant contributes data points for both frameworks and per-participant variance in skill, prior experience, and working style is absorbed into each pairwise comparison rather than confounding it. The single-platform, single-model design mirrors empirical enterprise adoption patterns: \citet{demireretal2025} report that more than 90\% of commercial LLM API workload concentrates on a single chosen model even when multi-homing is available.

Participants are drawn from a cohort of University students and working professionals with active access to GitHub Copilot, either through the GitHub Education Pack or through a standard premium subscription.

\subsubsection{Experimental Design}

Each participant completes the case study task twice: once with APM, once with Spec-kit. Each session is time-boxed to a maximum of three hours, after which the participant stops regardless of completion state. The order of the two frameworks is counterbalanced across participants, so that approximately half of the cohort encounters APM first and the other half encounters Spec-kit first. This counterbalancing lets us attribute any observed first-to-second session improvement to task familiarity rather than to the framework itself, and is analyzed explicitly under Learning Effects in Section~\ref{sec:results}.

The two sessions are isolated from one another using Git, so no code, state, or context from the first session can influence the second. Session isolation, a branch-and-patch workflow, and per-session submission packaging are documented in the evaluation appendix.

\subsubsection{Data Source}

Each session produces three artifacts that together form the participant submission: the \texttt{.patch} file generated from the session's isolated Git branch, the set of JSON chat exports produced by Copilot for every conversation opened during the session, and a post-session questionnaire response (described in Section~\ref{sec:questionnaire}). The chat exports provide structured records of every conversation (model identifiers, message timestamps, tool invocations, and per-message speaker roles), enabling programmatic extraction of both request-level and interaction-level metrics without manual annotation.

Because GitHub Copilot is billed per seat with a monthly premium-request allowance and a marginal per-request charge for overage consumption, the per-conversation request counts preserved in the export metadata correspond directly to the unit in which the buyer's cost is incurred.\footnote{Premium-request billing structure and overage rates documented at: \url{https://docs.github.com/en/billing/concepts/product-billing/github-copilot-premium-requests}} The Copilot procurement model (three-part tariff, plan allowances, and model multipliers) is described in the evaluation appendix.

APM's multi-agent workflow spans multiple Copilot conversations within a single session (one for the Planner, one for the Manager, and multiple for the Workers), while Spec-kit operates within a single conversation. To keep the two frameworks comparable, all metrics are computed by aggregating every conversation file belonging to a participant submission into a unified session-level view. Participant data is anonymized and encrypted before storage; the sanitization scheme is documented in the evaluation appendix.

\subsubsection{Post-Session Questionnaire}
\label{sec:questionnaire}

Each session concludes with a short post-session questionnaire that captures self-reported measures complementing the chat-export-derived metrics. The instrument records the participant's completion state (whether the three-hour cap was hit, the task was completed earlier, or the session was stopped early), prior familiarity with the framework, confidence in the submitted solution, and perceived framework effectiveness. It additionally captures five workload items adapted from the NASA Task Load Index, an established instrument for subjective workload assessment: mental demand, effort, frustration, verification burden, and prompt-engineering burden. In the second session, participants additionally report whether completing the task with the second framework felt easier, harder, or the same compared to the first. All scored items use a five-point Likert scale. Two optional free-text fields allow participants to elaborate on the comparison and provide general feedback. The questionnaire is submitted alongside the per-session data upload through the submission pipeline documented in the evaluation appendix.

\subsection{Metrics and Data Collection}
\label{sec:metrics}

The metrics are organized into three measurement dimensions (economic, process, and functional), followed by the statistical analysis plan that applies them. The subsections below specify each in turn.

\subsubsection{Economic}

The primary economic metric is \textbf{premium requests per session}: the total number of premium requests consumed across all conversations of a single framework session. Each participant contributes one APM-session count and one Spec-kit-session count for the same task, compared pairwise across the cohort. The metric maps directly onto the buyer's monthly-allowance exposure under Copilot's subscription-plus-quota procurement model. \citet{lambrechtseimskiera2007} show empirically that under this pricing structure, buyer tariff choice is driven by demand uncertainty rather than marginal price, with consumers steering toward allowance-based plans to hedge against bill variance, and \citet{liandkumar2022} identify predictable operating cost as a primary driver of SaaS pricing structure; the share of allowance consumed is therefore the buyer-relevant cost signal for subscription customers.

The secondary economic metric reports the same per-session count broken down by phase. Planning-phase and implementation-phase boundaries are detected automatically per framework; detection rules are documented in the evaluation appendix. The phase split locates where each framework spends its budget and exposes the source of any observed cost differential.

All sessions use a single underlying model, held fixed across both frameworks and across both sessions of each participant: GPT-5.3-Codex. This is a $1{\times}$ premium-request model, available on every plan tier relevant to the participant pool. Holding the model fixed at a uniform $1{\times}$ multiplier eliminates multiplier-induced variance, so that a difference in premium-request counts reflects a difference in framework behavior rather than a difference in model choice. The Copilot pricing structure, plan allowances, and multiplier mechanics are documented in the evaluation appendix.

The metric measures share of the monthly premium-request allowance consumed within the subscription-plus-quota procurement model; it does not measure dollar-equivalent inference cost. \citet{demireretal2025} report that the raw inference price of a comparably capable model has declined by roughly three orders of magnitude over the preceding two years and is decoupled from the subscription price. The subscription buyer is by definition insulated from that translation, so the procurement-model scoping is intentional rather than a defect.

\subsubsection{Process}

The process metrics capture the coordination burden each framework imposes on the user across a session, together with the reliability with which each framework's agents produce directly usable output. \citet{ziegleretal2024} identify acceptance of AI-generated output as the strongest observable predictor of perceived developer productivity; the reliability sub-metrics below operationalize acceptance-like signals from the tool-call and code-modification events preserved in the chat export.

Each user message is assigned to one of three buckets: short (brief acknowledgments or routing messages), protocol (framework-protocol messages such as APM handoff routing or Spec-kit slash-command invocations), and standard (substantive task-related prompts). The \textbf{behavior distribution} reports the share of each bucket in the session's total user-message count; the \textbf{behavior magnitude} reports the average character count per bucket. Together these views expose whether a framework's user burden is concentrated in mechanical message-shuttling (high protocol share, low magnitude) or in substantive problem-solving (high standard share, high magnitude).

\textbf{Session duration} is the wall-clock time from the first user message of the session to the last assistant message, bounded above by the three-hour cap. Sessions that hit the cap and sessions that complete earlier are distinguished using the completion state reported in the post-session questionnaire.

Three sub-metrics characterize the reliability of agent output. The \textbf{tool success rate} is the proportion of agent tool invocations that return a non-error result. The \textbf{tool retry rate} is the proportion of invocations followed within the same agent turn by a repeated call to the same tool with adjusted arguments, indicating that the first attempt failed or was rejected. The \textbf{user edit rate on terminal commands} is the proportion of terminal-execution tool calls whose command string was modified by the user before execution rather than executed verbatim, indicating a lack of trust in the generated command.

\subsubsection{Functional}

The functional dimension is evaluated against the 100-point grading rubric introduced in Section~\ref{sec:grading}, which scores baseline preservation (12 points), Python feature correctness (36 points), and C replica correctness (52 points). Prior empirical work on AI coding assistants, including \citet{cuietal2025} and \citet{paradisetal2024}, typically collapses task completion into a single binary outcome; the partial-credit structure preserves the granularity needed to compare frameworks on complex multi-component work.

\subsubsection{Analysis Plan}
\label{sec:analysis-plan}

Each paired framework comparison uses a paired $t$-test on the participant-level differences, reported alongside Cohen's $d$, a standardized effect-size estimate that expresses the mean difference between two groups in pooled-standard-deviation units, distinguishing statistical significance from practical significance. The economic, process, and functional metrics are each analyzed this way: total rubric score, per-category scores, completion rates, premium requests per session, phase-broken request shares, behavior distribution and magnitude per bucket, reliability sub-metrics, and session duration.

Correlations between cost, process, and functional metrics are reported as Pearson coefficients within each framework and across the combined cohort. These surface whether framework-induced variation in cost or process burden translates into functional outcomes.

Learning effects are analyzed separately across the counterbalanced orderings. A learning-effect matrix reports mean first-to-second-session improvement across both framework orderings for each metric; an order-effect comparison between APM-first and Spec-kit-first directions tests whether the order of exposure affects the improvement; and the aggregate first-to-second-session improvement across orderings gives the baseline task-learning estimate.

\subsection{Threats to Validity}

This subsection enumerates internal, external, and construct validity threats and the mitigations applied.

\subsubsection{Internal Validity}

\textbf{Learning effects from the within-subjects design.} Each participant completes the same task twice, and task familiarity from the first session can influence performance in the second. Counterbalancing the framework order across participants mitigates the framework-effect confound but does not eliminate the underlying learning curve. The Learning Effects analysis in Section~\ref{sec:results} quantifies the mean improvement between sessions across both orderings and is the primary defence against this threat.

\textbf{Self-reported versus observed measures.} Subjective developer-reported productivity often diverges from objective time-in-motion measurements, occasionally in the opposite direction \citep{beckeretal2025, pengetal2023}. This study pairs the instrumented, export-derived metrics with a post-session questionnaire covering workload, confidence, and perceived framework effectiveness (Section~\ref{sec:questionnaire}); observed divergences between self-report and instrument are reported as findings rather than absorbed as an unstated limitation. Residual risk remains: self-reports are subject to recall bias and social-desirability pressures that the instrument-side measurements cannot independently correct.

\subsubsection{External Validity}

\textbf{Generalization scope.} The case study is run on a single AI IDE platform with a single fixed model, against a complex software engineering task requiring two-language implementation and legacy-codebase research, in a setting positioned between lab and field conditions. In an empirical analysis of twelve commercial LLM use-case categories, \citet{demireretal2025} report that programming commands both the highest average intelligence index and the highest willingness to pay among buyers, so the testbed sits in the domain most sensitive to marginal AI capability but not in administrative, analytical, or creative workflows. Lab-style productivity measurements for AI coding assistants have exceeded enterprise field measurements by more than a factor of two, and experienced developers on mature codebases have been observed to be slower with AI than without \citep{pengetal2023, cuietal2025, beckeretal2025}; the case-study measurements are neither pure laboratory benchmarks nor natural-setting observations. Findings generalise within this scope and do not generalise to multi-platform settings, dynamic cross-model routing, simpler or less knowledge-intensive tasks, or pure laboratory or natural-setting conditions.

\textbf{Temporal decay of findings.} The AI coding assistant field is evolving rapidly. Not only effect sizes but also descriptive claims throughout this chapter (plan allowances, model multipliers, command sets, and framework releases) are tied to the May 2026 case-study date stated in Section~\ref{sec:evaluation}. \citet{lambrechtseimskiera2007} show that tariff-choice effects are highly sensitive to exact allowance and price parameters; findings that rest on specific Copilot pricing parameters are defensible against the May 2026 snapshot but may require re-estimation under materially different parameters.

\subsubsection{Construct Validity}

\textbf{Behavioral input buckets as process-efficiency proxy.} The short, protocol, and standard input buckets are defined for this study and extracted from the chat-export content. They are not validated against an external coordination-burden instrument such as the SPACE framework \citep{ziegleretal2024} or the NASA Task Load Index. Their validity as proxies for human coordination effort rests on face validity alone: the relative ordering of frameworks along these metrics is robust, but the absolute magnitude of differences is interpretive rather than calibrated.

\textbf{Instrument coverage limits.} The 100-point rubric captures correctness and robustness but not code quality, maintainability, security posture, or long-term technical debt; prior empirical work on AI coding assistants has consistently noted that code-quality dimensions are not captured by pass/fail functional measurement \citep{paradisetal2024, cuietal2025}, and this study inherits that limitation. Metric extraction is further limited to the per-conversation JSON chat exports that accompany each participant submission: inline code-completion events that are not part of a chat conversation are invisible to the metric set, so the reliability and process metrics characterise only the agent-driven portion of the workflow rather than the full IDE interaction.

\textbf{Grader environment parity.} The grading pipeline runs submitted patches against a Docker-based replica of the openeclass platform rather than against the live University of Athens instance that participants develop against. The replica environment (Docker image, fixture data, authentication stubs) is documented in the evaluation appendix. Divergences between the replica and the live instance (for example, timezone handling, localized date parsing, or session-cookie behavior) can in principle cause a patch that works locally to miss points during grading. Fixed baseline commits and deterministic seeded test data mitigate but do not eliminate this risk.
