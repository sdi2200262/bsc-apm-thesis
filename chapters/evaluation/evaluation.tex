\section{Methodology and Research Questions}
\label{sec:evaluation}

We evaluate the Agentic Project Management (APM) framework in a realistic setting through a comparative case study with human participants. The study compares APM, the multi-agent framework presented in Chapter~\ref{chap:framework-design}, against GitHub Spec-kit, the single-agent framework introduced in Chapter~\ref{chap:background}. The study was conducted in May 2026 on the Claude Code command-line interface, which both frameworks run on top of; pricing, model, and command-set statements in this chapter refer to that snapshot.

Both frameworks build on the spec-driven discipline of Section~\ref{sec:spec-driven}, approaching the task through explicit specification and planning, and each realises it in its own way. The most salient difference, and the one this comparison turns on, is whether that work is carried by a single agent or distributed across several. The evaluation probes that difference along four dimensions, defining the following Research Questions (RQs):

\begin{itemize}
    \item \textbf{RQ1 (Economic):} How does APM's multi-agent structure affect the dollar cost of completing a task relative to Spec-kit's single-agent workflow, and is that difference consistent across models of differing capability?
    \item \textbf{RQ2 (Process):} How does APM's multi-agent structure change the time a task takes and the effort it demands of the user, relative to Spec-kit's single-agent workflow?
    \item \textbf{RQ3 (Functional):} How do the two frameworks differ in functional outcome, in how much of the task each completes and in how they fail when they fall short?
    \item \textbf{RQ4 (Perception):} How does participants' self-reported experience of each framework relate to the behaviour measured from their sessions?
\end{itemize}

\section{Frameworks under Comparison}
\label{sec:frameworks}

The comparison sets APM against GitHub Spec-kit, two open-source frameworks that apply the spec-driven discipline of Section~\ref{sec:spec-driven} on top of an existing coding agent. APM's design is described in full in Chapter~\ref{chap:framework-design}; Spec-kit, the single-agent counterpart, is introduced here so the two can be read on the same terms.

Spec-kit\footnote{Documentation available at: \url{https://github.github.io/spec-kit/}} is GitHub's open-source spec-driven development toolkit. A single agent applies the discipline from end to end, producing the specification and the plan and then implementing them, all within one continuous conversation.

The work is driven by a set of slash commands that the developer triggers, or the agent autonomously invokes, each a bundle of instructions that walks the agent through one step of the workflow. The first is \texttt{/speckit-constitution}, which fixes the project's governing principles in a file; these come either from the user or from the agent's reading of the existing project, and the agent is to uphold them throughout. The specification is then built through three sequential commands:

\begin{enumerate}
    \item \texttt{/speckit-specify}: directs the agent to produce a structured specification of requirements, user stories, and acceptance criteria from a feature description.
    \item \texttt{/speckit-plan}: has it turn that specification into a technical implementation plan with architecture decisions, data models, and API contracts.
    \item \texttt{/speckit-tasks}: prompts it to derive an executable task list from the plan, annotated with dependencies and sequencing constraints.
\end{enumerate}

Finally, \texttt{/speckit-implement} has the agent work through the task list in sequence, while further commands support iterative refinement, cross-artifact consistency checking, and custom quality checklists along the way.

\section{Case-Study Design}
\label{sec:study-design}

The study is a within-subjects comparative case study across a homogeneous cohort of twelve participants drawn from university students and working professionals. Every participant completes the same task twice, once with each framework, so per-participant variance in skill, prior experience, and working style is absorbed into each pairwise comparison rather than confounding it. The cohort therefore yields twenty-four sessions in total.

\subsection{Task Specification}

The task is delivered to each participant as a complete product requirements document (PRD), in the form a developer receives a real feature brief.\footnote{Task specification, participant package, and containerised testing environment available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-task}} It builds on \texttt{eclass-mcp-server},\footnote{Repository available at: \url{https://github.com/sdi2200262/eclass-mcp-server}} an existing open-source Python Model Context Protocol (MCP)\footnote{Protocol specification available at: \url{https://modelcontextprotocol.io}} server that connects to Open eClass,\footnote{Repository available at: \url{https://github.com/gunet/openeclass}} the learning-management platform used across Greek universities. Participants extend the server with two new announcement-retrieval tools, then reimplement it in full, including those tools, as a standalone native C replica under strict constraints.

The work is deliberately broad. Building the new tools requires investigating the unfamiliar legacy PHP codebase behind Open eClass, to learn how it exposes its data, and implementing them in Python. The C replica reproduces the entire server from scratch as a standalone, drop-in microservice, covering not just the tool logic but the protocol layer that the Python server gets from the MCP SDK. It must additionally meet strict constraints on manual data handling and memory safety. Spanning a legacy system and two implementation languages, the task sets both frameworks a demanding, end-to-end engineering workload.

\subsection{Task Environment}
\label{sec:task-env}

Each participant runs the study inside a fresh, dedicated Linux virtual machine, prepared in advance, so all their work happens in the same isolated environment. The machine provides the development toolchain the task needs and a workspace holding the PRD, a clone of \texttt{eclass-mcp-server} at a fixed baseline against which the participant works, and a clone of the Open eClass codebase the agent can investigate. A containerised Open eClass instance, built from that same fixed version of the platform and seeded with a fixed set of mock data, runs in the background throughout the session alongside a mock single-sign-on service, so the participant and the agent can validate their work against the running platform. Every participant therefore develops against the same fixed state.

\subsection{Sessions and Data}
\label{sec:sessions-data}

Each of a participant's two sessions is time-boxed to a maximum of three hours, within which the participant carries out the task with the assigned framework and then answers a short post-session questionnaire. Between the two sessions the environment is reset to its initial baseline, so that no code, workspace state, or assistant context from the first session carries into the second.

Two factors are counterbalanced across the cohort: the framework order and the model assignment. The framework-order factor varies which framework a participant encounters first; counterbalancing it lets any first-to-second-session improvement, a learning effect from growing task familiarity, be distinguished from the framework's own effect. These learning effects are analysed in the Learning Effects subsection in Section~\ref{sec:results}. The model factor holds one Claude model fixed across both of a participant's sessions. Each participant is assigned either Claude Opus 4.7 or Claude Sonnet 4.6, the two models Claude Code offered during the study window, which differ in capability and in context-window capacity, one million tokens for Opus against two hundred thousand for Sonnet. Crossing the two factors gives four assignment cells of three participants each.

From each session we collect a participant submission of three parts: the solution patch the participant writes against the baseline, the session transcripts the command-line interface records for every conversation opened, and the participant's response to a post-session questionnaire.

\section{Measures}
\label{sec:metrics}

Every measurement defined in this section is extracted from a participant's submission by the same procedure across the cohort. The economic, process, and supplementary measurements are computed programmatically from the session transcripts; the functional measurements are computed from the solution patch by an automated grader, against a fixed scoring rubric; and the self-reported perception measurements come from the post-session questionnaire.

Each transcript-derived measurement is computed at more than one scope, a scope being the portion of a session it is aggregated over. The session scope is the whole session, the headline on which the two frameworks are compared, since it puts APM's multi-conversation workflow and Spec-kit's single conversation on the same denominator. The phase scope splits the session into its planning and implementation portions and shows how each measurement divides between them. The role scope applies to APM alone, since Spec-kit has no agent roles to separate, and is a descriptive, deeper look at how each measurement is spread across its agents. The functional dimension admits no such split and is reported at the session scope alone.

Each measurement is classed as Primary, Secondary, or Supplementary. Primary measures are the ones compared between the two frameworks to answer a research question; Secondary measures break down or support a Primary; Supplementary measures are descriptive only. The subsections below specify each measurement dimension in turn.

\subsection{Economic}

The primary economic measurement is the \textbf{dollar-equivalent cost}, computed by pricing every call recorded in the session's transcripts against Anthropic's published per-token rate card at the study's snapshot date. Calls made by the conversation's primary agent are priced at that conversation's declared model; calls made by subagents are priced against the model recorded in the platform's sibling subagent transcript for that dispatch. Each participant contributes one APM cost and one Spec-kit cost for the same task, compared pairwise across the cohort at the session scope. This cost is broken down further to locate where the spending accrues, across the planning and implementation phases, by token category, and for APM across its agent roles.

\subsection{Process}

The process measures capture two things, the effort each framework demands of the user, seen in how the user interacted with the agent, and the time the task takes, seen in the session's timing.

User messages are characterised along two dimensions. The first is the kind of message:
\begin{itemize}
    \item a \textbf{turn prompt} is a message submitted while the agent is idle, opening a new turn, the wall-clock interval from the prompt to the agent's idle return.
    \item a \textbf{steer} is an interjection enqueued while the agent is still working, which the platform either delivers to the agent during the turn or abandons if the user retracts it before delivery.
\end{itemize}
The second is the content bucket, which sorts each prompt and delivered steer by whether it invokes a framework command and, otherwise, by its length:
\begin{itemize}
    \item \textbf{protocol} for an APM or Spec-kit framework command.
    \item \textbf{short} for a brief, non-command message below a length threshold, like a quick acknowledgment or a choice of options.
    \item \textbf{standard} for a longer, substantive message at or above it, such as a course correction, a decision, or guidance.
\end{itemize}

The primary interaction measures are the counts of turn prompts and of delivered and attempted steers, together with two bucket views. The \textbf{bucket-share distribution} reports the share of each bucket in the session's user-message count, separately for prompts and for delivered steers and jointly across both, and the \textbf{magnitude per bucket} reports the mean character count of messages in each bucket. Together these expose whether the user's effort goes into mechanical message-shuttling (high protocol share, low magnitude) or into substantive corrections and guidance (high standard share, high magnitude).

The temporal shape of the session is captured by two primary measures, the session duration and the turn count, and two secondary ones that decompose the time within it, the turn time and the inter-turn time:
\begin{itemize}
    \item \textbf{session duration} is the wall-clock span from the first user message of the session to the last assistant message, bounded above by the three-hour cap.
    \item \textbf{turn count} is the number of turns recorded across the session's conversations.
    \item \textbf{turn time} is the wall-clock union of every turn's interval, reported in total and split into the share spent in a single conversation at a time (\textbf{solo}) and the share where two or more conversations were active at once (\textbf{concurrent}); for APM this surfaces whether the participant ran agents in parallel or serially.
    \item \textbf{inter-turn time} is the residual of the session duration once turn time is subtracted, the wall-clock gap between consecutive turns summed across the session. It is the assistant's idle time as recorded in the transcripts, not read as a measure of participant activity, since a gap may be spent reading, thinking, switching context, or away from the task entirely.
\end{itemize}

These timing measures are reported at session and phase scope only; at role scope the wall-clock union and concurrency interpretations are not well-defined, since a role lives inside a single conversation whose turns cannot overlap.

\subsection{Functional}

The functional dimension is scored by an automated grader that runs a fixed rubric of behavioural assertions against each submission.\footnote{Grader, scoring rubric, and the rest of the evaluation infrastructure available at: \url{https://github.com/sdi2200262/bsc-apm-case-study-infra}} The grader observes only the running server's responses and the compiled C binary, never the participant's source, so it is indifferent to how the solution is built. The rubric is a fixed set of ninety atomic checks, each testing one expected behaviour and carrying a calibrated point weight toward a 100-point total.

Each check returns one of three verdicts. A \textbf{passed} check matches an accepted form and earns its full points; a \textbf{partial} check matches none but lands near one, earning its points scaled by its similarity to the nearest form and flagged for review; a \textbf{failed} check earns zero. A submission therefore earns proportionally for what works, and its score separates a strict part, the full points of the passed checks, from a partial part, the fractional credit of the near-misses.

The 100 points split across the task's two implementations, 30 on the Python extension and 70 on the heavier C replica, and within each across sections covering the pre-existing tools, the new features, and, for the C replica, its build and memory safety.

The primary functional outcome is the \textbf{total score}, which summarises the comparison in a single number. The \textbf{per-section scores} decompose it across the rubric's sections, locating where each framework's work lands.

\subsection{Supplementary}

A small set of supplementary descriptors is reported per framework alongside the primary and secondary measures. They are descriptive only and are not part of the framework comparison, kept to characterise each session.

The \textbf{tool success rate} is the proportion of the session's main-transcript tool-invocation results that carry no error flag, across every tool the assistant may invoke and without weighting by tool kind; calls made inside subagent dispatches are excluded. It is a descriptive check on the reliability of the session's tool use.

The next three descriptors are proxies for the agent acting on its own initiative, behaviour the platform permits under either framework. The \textbf{subagent dispatch count} is the number of subagent dispatches the main agent issued in scope, and the \textbf{delegated tool-use count} is the number of tool invocations those subagents performed in their own conversations; together they measure how much work is offloaded to delegated subagents. The \textbf{model-invoked Skill count} is the number of Skill bodies the agent itself caused to be injected, without a user typing the command, capturing self-invocation that does not appear in the user-message activity.

\section{Analysis Plan}
\label{sec:analysis-plan}

Each measurement is reported at the cohort level as a descriptive summary first (mean, standard deviation, median, and inter-quartile range per framework and per model band) and then as a paired framework comparison. The descriptive summaries report what a typical APM session and a typical Spec-kit session cost, take, and produce, and locate the spread of the cohort around those typical values. The paired comparison establishes whether the per-participant difference between the two frameworks is systematic across the cohort and how large that difference is relative to the per-participant variance.

The paired comparison uses a paired $t$-test on the per-participant difference. Given the two paired values $x_i^{\text{APM}}$ and $x_i^{\text{SK}}$ for participant~$i$, the difference $d_i = x_i^{\text{APM}} - x_i^{\text{SK}}$ has mean $\bar{d}$ and standard deviation $s_d$ across the cohort of $n$ participants; the test statistic is
\[
    t = \frac{\bar{d}}{s_d / \sqrt{n}},
\]
and the reported $p$-value comes from the two-sided $t$ distribution on $n - 1$ degrees of freedom.

The effect size is Cohen's $d_z$, the standardised mean difference in pooled within-pair-variance units,
\[
    d_z = \frac{\bar{d}}{s_d},
\]
which expresses the framework gap in standard deviations rather than in the metric's native units and so makes effect sizes comparable across metrics of different scale.

Every primary measurement is analysed this way: total rubric score, per-section scores, per-session cost, phase-broken cost shares, bucket-share distribution and magnitude per bucket across turn prompts and delivered steers, the turn-time decompositions, and session duration. The model factor is handled by stratification: paired comparisons are reported within each model band and then jointly across the cohort, exposing any framework effect that holds in one band but not the other.

Correlations between economic, process, and functional metrics are reported as Pearson coefficients within each framework and across the combined cohort. Pearson's $r$ is the standardised linear-association statistic on the pair $(x_i, y_i)$:
\[
    r = \frac{\sum_i (x_i - \bar{x})(y_i - \bar{y})}{\sqrt{\sum_i (x_i - \bar{x})^2 \, \sum_i (y_i - \bar{y})^2}},
\]
taking values in $[-1, 1]$. Correlation magnitudes are interpreted alongside the within-framework spread; they surface whether framework-induced variation in cost or process burden translates into functional outcomes.

Learning effects are analysed separately across the counterbalanced orderings. A learning-effect matrix reports mean first-to-second-session improvement across both framework orderings for each metric; an order-effect comparison between APM-first and Spec-kit-first directions tests whether the order of exposure affects the improvement; and the aggregate first-to-second-session improvement across orderings gives the baseline task-learning estimate.

\subsection{Threats to Validity}

This subsection enumerates the internal, external, and construct validity threats and the mitigations applied. Each threat points back to the specific subsection that motivates it.

\subsubsection{Internal Validity}

\textbf{Learning effects from the within-subjects design.} The within-subjects design declared in the Study Design subsection in Section~\ref{sec:evaluation} has each participant complete the same task twice, so task familiarity from the first session can influence performance in the second. Counterbalancing the framework order across participants, as described in the Counterbalancing subsection in Section~\ref{sec:evaluation}, mitigates the framework-effect confound but does not eliminate the underlying learning curve. The Learning Effects analysis described in the Analysis Plan subsection in Section~\ref{sec:evaluation} quantifies the mean improvement between sessions across both orderings and is the primary defence against this threat.

\textbf{Self-reported versus observed measures.} The post-session questionnaire described in the Post-Session Questionnaire subsection in Section~\ref{sec:evaluation} pairs the instrumented, transcript-derived metrics with self-reported workload, confidence, and perceived framework effectiveness; observed divergences between self-report and instrument are reported as findings rather than absorbed as an unstated limitation. Residual risk remains: self-reports are subject to recall bias and social-desirability pressures that the instrument-side measurements cannot independently correct.

\subsubsection{External Validity}

\textbf{Generalisation scope.} The case study is run on a single AI coding CLI, against a complex software engineering task requiring two-language implementation and legacy-codebase research, described in the Task Description subsection in Section~\ref{sec:evaluation}, in a setting positioned between laboratory and field conditions. Findings generalise within this scope and do not generalise to multi-platform settings, dynamic cross-model routing, simpler or less knowledge-intensive tasks, or pure laboratory or natural-setting conditions.

\textbf{Temporal decay of findings.} The AI coding assistant field is evolving rapidly. Effect sizes and descriptive claims throughout this chapter (rate-card prices, command sets, framework releases, and model availability) are tied to the May 2026 snapshot stated in Section~\ref{sec:evaluation}. The dollar-equivalent cost values reported under Section~\ref{sec:results} rest on the rate-card snapshot; results that rest on those specific rates are defensible against the snapshot but may require re-estimation under a materially different rate card.

\subsubsection{Construct Validity}

\textbf{Behavioural input buckets as process-efficiency proxy.} The short, protocol, and standard input buckets defined under the Process metric in the Metrics and Data Collection subsection in Section~\ref{sec:evaluation} are extracted from the transcript content for this study. They are not validated against an external coordination-burden instrument. Their validity as proxies for human coordination effort rests on face validity alone: the relative ordering of frameworks along these metrics is robust, but the absolute magnitude of differences is interpretive rather than calibrated.

\textbf{Instrument coverage limits.} The 100-point rubric captures correctness and robustness but not code quality, maintainability, security posture, or long-term technical debt. Metric extraction is further limited to the Claude Code JSONL transcripts and their sibling subagent files that accompany each participant submission, as declared in the Data Source subsection in Section~\ref{sec:evaluation}: any interaction with the AI that took place outside the CLI's transcript surface is invisible to the metric set.

\textbf{Replica versus live openeclass.} The shared Docker-based replica of the openeclass platform described in the Task Environment subsection in Section~\ref{sec:evaluation} pins the platform to a fixed upstream baseline and seeds deterministic fixture data. The shared replica makes the cohort comparable and the grading reproducible, and removes any parity gap between what participants build against and what the evaluation runs against. The trade-off is that the task is performed against a replica rather than against any live university instance of openeclass: any property of a live instance that the replica does not reproduce, such as timezone handling of locale-formatted dates, session-cookie behaviour under load, cross-origin interactions with the mock CAS service, or upstream behaviours that have shifted since the baseline commit, is not exercised by the case study.
