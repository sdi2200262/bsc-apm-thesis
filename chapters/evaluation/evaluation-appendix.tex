\subsection{Test Suite Structure}

The automated test suite evaluates submissions across three categories (48 points total):

\begin{itemize}
    \item \textbf{Python Baseline (12 points)} - Tests existing functionality from main branch (11 test cases: build, protocol, login, logout, courses, authstatus)
    
    \item \textbf{Python Feature (12 points)} - Tests new \texttt{get\_course\_announcements} implementation (5 test cases: error handling, date filtering, output format)
    
    \item \textbf{C Replica (24 points)} - Tests complete C implementation (16 test cases: compilation, memory safety, protocol compliance, all tool functionality)
\end{itemize}

\noindent Test definitions and point allocations are specified in \texttt{grader/src/scorer.py}. Test execution logic is implemented in:
\begin{itemize}
    \item \texttt{grader/src/protocol\_tester.py} - MCP protocol and tool functionality tests
    \item \texttt{grader/src/memory\_tester.py} - Valgrind memory leak detection
    \item \texttt{grader/src/build\_tester.py} - Build system verification
\end{itemize}

\noindent For the detailed scoring rubric, see: \ghlink{bsc-apm-case-study-task/task/SCORING.md}{https://github.com/bsc-apm-case-study-task/blob/main/task/SCORING.md}\newline

\subsection{Submission Workflow and Format}

This section describes the complete participant submission process: what participants do, how they ensure session isolation, and what they deliver.

\subsubsection{Task Workflow}

Participants complete the task in two isolated sessions, each using a different AI tool. The workflow for each session is:

\begin{enumerate}
    \item Create an isolated Git branch from the clean baseline
    \item Work on the task using the assigned AI tool
    \item Generate submission artifacts (code patch and interaction logs)
    \item Clean up the session branch to ensure isolation
\end{enumerate}

\subsubsection{Session Isolation Mechanism}

To ensure clean separation between sessions and minimize learning effects from contaminating results, participants work on isolated Git branches:

\begin{enumerate}
    \item \textbf{Session 1:} Create branch \texttt{s1\_\{tool\}} from clean \texttt{main} branch
    \item Work on task, commit changes to session branch
    \newpage
    \item Generate the solution patch as the diff between \texttt{main} and the session branch, named according to the submission convention (see Section~\ref{sec:submission-format}).
    \item Export logs and save patch to safe location
    \item Delete session branch: \texttt{git branch -D s1\_\{tool\}}
    \item \textbf{Session 2:} Repeat process with \texttt{s2\_\{tool\}} branch
\end{enumerate}

\noindent This workflow ensures that:
\begin{itemize}
    \item Each session starts from an identical baseline state
    \item No code or context from Session 1 influences Session 2
    \item Patches accurately represent only the changes made during that specific session
\end{itemize}

\subsubsection{Submission Format and Contents}
\label{sec:submission-format}

Submissions follow a strict naming format to enable automated processing:

\noindent \underline{\texttt{\{PID\}\_\{S1|2\}\_\{platform\}\_\{tool\}\_submission.zip}}\newline

\noindent Where:
\begin{itemize}
    \item \texttt{\{PID\}} - Participant ID (e.g., \texttt{P001})
    \item \texttt{\{S1|2\}} - Session number (\texttt{S1} for first tool, \texttt{S2} for second tool)
    \item \texttt{\{platform\}} - Platform identifier: \texttt{cursor} or \texttt{copilot} (lowercase)
    \item \texttt{\{tool\}} - Tool identifier: \texttt{apm}, \texttt{spec-kit}, \texttt{cursor-plan}, or \texttt{copilot-plan} (lowercase, hyphenated)
\end{itemize}

\noindent Example: \texttt{P001\_S1\_cursor\_apm\_submission.zip}\newline

\noindent Each submission zip file must contain exactly two items at the root level:

\begin{enumerate}
    \item \textbf{Patch file} - \texttt{\{PID\}\_\{S1|2\}\_\{platform\}\_\{tool\}\_solution.patch}
    \begin{itemize}
        \item Git patch file created via \texttt{git diff main s\{1|2\}\_\{tool\}}
        \item Contains all code changes for the session
    \end{itemize}
    
    \item \textbf{Logs folder} - \texttt{\{PID\}\_\{S1|2\}\_\{platform\}\_\{tool\}\_logs/}
    \begin{itemize}
        \item \texttt{chats/} - Exported chat conversations (\texttt{.md} for Cursor, \texttt{.json} for Copilot)
        \item \texttt{stats/} - (Cursor only) Filtered CSV usage statistics
    \end{itemize}
\end{enumerate}

\subsection{Data Privacy and Anonymization}
\label{sec:privacy}

To protect participant privacy while enabling reproducibility, all chat exports are processed through anonymization and sanitization procedures before storage. This process is performed during the parsing stage of the grading pipeline.

\subsubsection{Metadata Preservation}

Each chat conversation is assigned a unique identifier using cryptographic hashing for anonymous cataloging:

\begin{itemize}
    \item \textbf{Method:} SHA256 hash of concatenated user messages
    \item \textbf{Format:} First 16 hexadecimal characters of the hash
    \item \textbf{Purpose:} Enables unique identification of chats without revealing participant identity or conversation content
\end{itemize}

\noindent The chat ID is computed before sanitization and preserved in plaintext metadata, allowing cataloging and deduplication without decryption. Along with the chat ID, the following metadata is preserved in plaintext:

\begin{itemize}
    \item \textbf{Model IDs:} Distinct language models used in the conversation
    \item \textbf{Request Count:} Total number of AI requests in the chat
    \item \textbf{Timestamp:} Sanitization timestamp
    \item \textbf{Original Size:} Size of original payload in bytes
\end{itemize}

\noindent This metadata enables dataset organization, integrity validation, and basic analysis without requiring access to encrypted content.

\subsubsection{Sanitization Process}

Chat exports are sanitized using reversible encryption to protect sensitive information such as file paths, command histories, and timestamps:

\begin{itemize}
    \item \textbf{Encryption Method:} HMAC-SHA256 XOR cipher
    \begin{itemize}
        \item Keystream generation via HMAC-SHA256 expansion with random salt
        \item XOR encryption of serialized chat payload
        \item Base64 encoding of salt and ciphertext
    \end{itemize}
    \item \textbf{Storage Format:} \texttt{ENC:<salt\_b64>:<ciphertext\_b64>}
    \item \textbf{Reversibility:} Decryption using the shared secret produces data bitwise-identical to the original
\end{itemize}

\noindent For implementation details, see: \ghlink{bsc-apm-case-study-task/grader/scripts}{https://github.com/bsc-apm-case-study-task/tree/main/grader/scripts}

\subsection{Grading Pipeline Architecture}

The grading infrastructure processes submissions through a multi-stage pipeline with checkpoint-based error recovery. Each stage is logged in a manifest file (see Section~\ref{sec:manifest}) with checksums and timestamps for audit trails and reproducibility.

\subsubsection{Pipeline Stages}

The submission processing workflow consists of six discrete stages:

\begin{enumerate}
    \item \textbf{Validation} (\texttt{pipeline/validate\_submission.py}) - Validates zip structure and naming format, extracts submission to workspace root.

    \item \textbf{Grading} (\texttt{pipeline/grade\_submission.py}) - Runs the automated black-box test suite against the Python and C implementations and writes results to JSON and TXT files.

    \item \textbf{Parsing} (\texttt{pipeline/parse\_submission.py}) - Extracts interaction metrics from chat exports and sanitizes chat logs using reversible encryption (see Section~\ref{sec:privacy} for details).

    \item \textbf{Combination} (\texttt{pipeline/combine\_participant.py}) - Merges grading results with extracted interaction metrics into unified participant result files.

    \item \textbf{Dataset Aggregation} (\texttt{pipeline/add\_to\_dataset.py}) - Appends processed submission data to platform-level CSV datasets.

    \item \textbf{Integrity Validation} (\texttt{pipeline/validate\_dataset.py}) - Validates dataset integrity against manifest checksums and timestamps.
\end{enumerate}

\noindent For detailed pipeline documentation, see \texttt{grader/PIPELINE.md} in the case study repository (linked under Additional Resources).

\subsection{Pipeline Manifest System}
\label{sec:manifest}

The pipeline uses a manifest-based checkpointing system for traceability and error recovery. Each platform maintains a manifest at:

\noindent \underline{\texttt{submissions\_sanitized/\{platform\}/pipeline\_manifest.json}}

\subsubsection{Manifest Structure}

Manifest entries use key format: \texttt{\{PID\}\_\{S1|2\}\_\{Platform\}\_\{Tool\}}

\noindent Each entry tracks:
\begin{itemize}
    \item \textbf{Validation} - Zip checksum, extraction timestamp, validation status
    \item \textbf{Grading} - Test results, scores, grading timestamp
    \item \textbf{Parsing} - Metrics extraction status, sanitization checksums
    \item \textbf{Combination} - Merged result file checksum
    \item \textbf{Dataset} - CSV row checksum, dataset append timestamp
    \item \textbf{Validation} - Integrity check results
\end{itemize}

\noindent The processing history for any submission can be queried via:\newline
\ghlink{bsc-apm-case-study-task/grader/pipeline/inspect\_submission.py}{https://github.com/bsc-apm-case-study-task/blob/main/grader/pipeline/inspect\_submission.py}.
