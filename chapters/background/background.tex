\section{AI Assistants and Agents}
\label{sec:background-ai-assistants-and-agents}

The tools that assist developers as they write code have changed quickly, from completing a single line to carrying out whole tasks on their own. Integrated development environments have offered identifier and interface completion since the 1990s. By the late 2010s, machine-learning models trained on large code corpora ranked those suggestions. Such systems retrieve and rank symbols that already exist; they do not compose new code. The generative shift came when large language models (LLMs), whose training data includes large quantities of code, began producing novel, multi-line completions in the editor. GitHub Copilot brought this form to a wide audience in 2021.\footnote{GitHub Copilot technical preview, June 2021: \url{https://github.blog/2021-06-29-introducing-github-copilot-ai-pair-programmer/}.} A distinct mode of interaction followed in late 2022, when general-purpose conversational assistants based on LLMs reached the public. These were not explicitly coding tools, but developers used them to explain unfamiliar code, stand in for documentation, think through a problem, and draft code snippets to copy and paste. This conversational mode soon entered the editor and then moved from advice to action. AI assistants began acting directly on software projects. Tools of this kind emerged over 2024 and 2025.\footnote{Early examples include Devin, announced in March 2024 as an autonomous ``AI software engineer'' acting on a project from its own sandboxed environment rather than the developer's editor (\url{https://www.cognition.ai/blog/introducing-devin}), and GitHub Copilot's agent mode, introduced in February 2025, which works inside the editor to plan a task, edit across multiple files, run commands, and iterate on the results (\url{https://code.visualstudio.com/blogs/2025/02/24/introducing-copilot-agent-mode}).} It is this conversational line, rather than inline completion, that the systems studied in this thesis descend from.

We use the term \emph{agent} in a specific sense. In its classical formulation, an agent is anything that perceives its environment through sensors and acts upon that environment through actuators \cite{russell2021aima}. In an LLM-based agent, the model serves as the central controller within an iterative loop. The surrounding system provides planning and memory and equips the model with perception and action mechanisms through which it can use tools and respond to its environment \cite{liu2024llmagents}. Within the loop, the model reasons about the goal, chooses an action, observes the result, and decides what to do next \cite{yao2023react}. Throughout this thesis, \emph{agent} refers to a model-directed system with these capabilities. A \emph{coding agent} applies them to a software project, allowing the model to inspect and edit files, run commands, and revise its work against the results.

LLM-based agents appear in two forms relevant to this thesis. A purpose-built application can implement an agent by calling a model through its programming interface, assembling the context it receives, exposing tools, and routing its outputs in code. Alternatively, an interactive coding agent can package that machinery as a general development tool to which the developer assigns work directly. A framework can then operate on top of that coding agent by supplying natural-language instructions, roles, and procedures for it to follow.

Attempts to measure the effect of these tools on developer productivity have reached conflicting conclusions across different generations of the technology. Field experiments with an earlier generation of assistants reported substantial gains. One study pooled three randomised controlled trials at Microsoft, Accenture, and a Fortune-100 company, in which nearly five thousand professional developers using an AI assistant completed around a quarter more tasks, with the clearest gains among the less experienced \cite{cui2026genai}. A later METR trial of early-2025 tools reached the opposite result among experienced open-source developers working on large repositories to which they regularly contributed. When allowed to use AI tools, primarily the Cursor editor\footnote{Cursor, an AI code editor: \url{https://cursor.com}.} with Claude 3.5 and 3.7 Sonnet, they were roughly 19\% slower even as they expected the tools to speed them up \cite{becker2025metr}. Their models, tools, tasks, and participants differ, so the effect appears conditional rather than settled. Like the wider productivity literature in this field, both ask only whether AI assistance helps. Neither varies the workflow or framework through which a developer works with the agent, the dimension this thesis sets out to compare.

\section{Context Windows and Context Decay}
\label{sec:background-context-windows-and-context-decay}

Whatever its form, an agent is built on a model that accepts input and produces output in units called tokens. The model itself does not retain the session between independent calls. Between calls, the surrounding coding agent preserves the session's continuity by assembling prior messages, tool results, and other retained content as the next call's \emph{context}. The \emph{context window} bounds the span of input and output that the model can process in that call. This context can include the system prompt, the agent's instructions, preceding exchanges, tool calls and their results, and file contents introduced along the way. The new output then becomes part of the history on the following call. At the time of writing, a frontier model's context window spans several hundred thousand to a million tokens, yet a long real-world task can still reach that limit.\footnote{Anthropic's documentation illustrates these mechanics for the models and coding agent used in this study: context windows, \url{https://platform.claude.com/docs/en/build-with-claude/context-windows}; prompt caching, \url{https://platform.claude.com/docs/en/build-with-claude/prompt-caching}; and compaction, \url{https://platform.claude.com/docs/en/build-with-claude/compaction}.}

The growing history creates pressure on both capacity and cost. Bringing the session closer to the context-window limit makes each later call process more input tokens than the one before it. Because model use is priced by the input and output tokens processed, the total input cost of a long session can grow faster than its number of turns \cite{gao2025turncontrol}. Prompt caching can lower the price of a repeated prefix, but it does not remove those tokens from the context window, and cache reads and writes remain billable.

A model does not use this growing context evenly. Controlled experiments on long-context models found a U-shaped pattern. Performance is highest when the relevant information sits at the start or the end of the input and falls sharply when it lands in the middle \cite{nliu2023lostmiddle}. Usable capacity is therefore smaller than the raw token count suggests. In a coding session, subsequent exchanges push earlier decisions and instructions deeper into the history, where they can become harder to recover. The agent may then overlook decisions or completed work and drift from the original goal \cite{liu2024llmagents}.

One response is \emph{compaction}. As a conversation approaches its limit, the coding agent replaces earlier history with a shorter summary and continues from it. This reset frees space in the context window and reduces the input carried into the next call, but the omitted detail is no longer directly available to the model. Compaction therefore exchanges fidelity for capacity rather than eliminating the accumulation problem.

Together, the decline in reliability and the rise in cost have made deliberate management of the context window a concern in its own right. Early practice centred on \emph{prompt engineering}, structuring the natural-language input given to a model to elicit a particular response. As work grew into long agentic sessions, the harder question became what the context window should hold at each step, not only how to phrase a single request. This wider practice manages the whole body of context supplied to a model so that the agent's limited attention and tokens remain focused on relevant material. It is known as \emph{context engineering}. The strategies described through the rest of this chapter are different responses to the accumulation problem it addresses.

\section{Spec-Driven Development}
\label{sec:background-spec-driven-development}

One way to keep an agent focused is to give it a durable specification of what it should build before implementation begins. In AI-assisted development, this approach is known as \emph{spec-driven development} (SDD). Its underlying principle predates AI. Design by Contract, described in 1992, makes the specification part of the program itself. It attaches to each routine the conditions assumed on entry, the guarantees required on exit, and the invariants preserved throughout \cite{meyer1992dbc}. Test-driven development (TDD), codified in 2002, reverses the usual order of coding and testing. It begins with tests that define correct behaviour, so an executable specification of what the code must do precedes the code itself \cite{beck2002tdd}. The name has an earlier history of its own. In 2004, an approach called specification-driven development combined TDD with Design by Contract, treating tests and contracts as complementary kinds of specification \cite{ostroff2004specdriven}. In this thesis, SDD refers to the current AI-assisted practice.

Beyond defining the intended software, the specification helps manage the agent's context. When developers improvise instructions turn by turn, their intent remains only in a lengthening conversation and can become difficult to recover. SDD instead fixes that intent in a durable artefact written before the code. The conversation still grows, but the agent can return to the specification, bring the goal back into context, and check its work against it. SDD is therefore one context-engineering strategy.

As a named practice in AI-assisted development, SDD took shape over 2025 in tools at different implementation layers. Amazon's Kiro, released in July as an interactive coding agent and development environment, built the practice into the tool itself. Its agent carries a developer from natural-language requirements through a design to sequenced implementation tasks.\footnote{Kiro, introduced in July 2025 as an agentic development environment with spec-driven development as its named workflow: \url{https://kiro.dev/blog/introducing-kiro/}.} GitHub's Spec-kit, released in September, instead supplies an external toolkit that brings a sequence that includes specification, planning, and implementation to an existing coding agent. It turns specifications into software on the premise that the \emph{spec}, not the code, is the source of truth.\footnote{GitHub Spec-kit, described as an open-source spec-driven development toolkit for coding-agent workflows, September 2025: \url{https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/}.}

In the core workflows introduced by both tools, one agent carries the specification through planning and implementation. The spec-driven discipline itself does not determine how many agents perform the work.

\section{Multi-Agent Systems}
\label{sec:background-multi-agent-systems}

Another context-engineering strategy distributes work across several agents. A multi-agent system (MAS) consists of agents whose interactions contribute to a shared task. Their organisation varies: agents may approach the same problem from different perspectives, take specialised roles, or receive separate parts of a decomposed task \cite{cemri2025masfail}. In the decomposed form relevant to this thesis, each part can be handled in its own context, reducing the history burden on any one conversation and allowing independent work to proceed in parallel. The value of this design depends on how readily the work can be divided and how well the agents coordinate. Whether it actually produces better software than one capable agent is far from settled.

Multi-agent systems have a long history in artificial intelligence, where they describe collections of autonomous entities acting within a shared environment \cite{russell2021aima}. Capable language models prompted a wave of research that applied the idea to LLM-based agents. During 2023, several systems organised these agents into role-specialised teams, including teams applied to software tasks. CAMEL paired agents in a structured dialogue \cite{li2023camel}, ChatDev cast them as the staff of a virtual software company \cite{qian2024chatdev}, while MetaGPT coordinated them through the documents and standard procedures of a development process \cite{hong2024metagpt}. Microsoft's open-source AutoGen framework supported collaborative conversations between agents that solved complex problems and wrote code \cite{wu2024autogen}. These research systems belong to the purpose-built form introduced earlier. Their application code assembles the context and tools for each agent and routes messages between them, while the models choose actions within that scaffold.

The evidence that this approach improves performance compared with a single agent is weak. One study analysed more than sixteen hundred execution traces from seven multi-agent frameworks and found recurrent failures across their workflows, while gains over single-agent systems or simpler baselines were often minimal \cite{cemri2025masfail}. A separate empirical comparison found that the advantage of a MAS narrows as the underlying model grows more capable, so much of the benefit seen with weaker models recedes with stronger ones \cite{gao2025singlemulti}. Together, these results suggest that any improvement from division of labour is neither reliable nor stable as the models improve.

Practitioner accounts identify similar limits for agents used in software development. Anthropic reports a large gain from a multi-agent system over a single agent on open-ended research, but attributes that gain to the breadth of parallel search allowed by the task and identifies coding as a poor fit. Most coding work, it notes, divides into fewer genuinely independent pieces and depends on context that every agent would need to share.\footnote{Anthropic, ``How we built our multi-agent research system'', 13 June 2025: \url{https://www.anthropic.com/engineering/multi-agent-research-system}.} Cognition similarly argues that splitting coding work disperses decisions and prevents agents from sharing enough context, leaving the resulting systems fragile.\footnote{Cognition, ``Don't Build Multi-Agents'', 12 June 2025: \url{https://cognition.ai/blog/dont-build-multi-agents}.} Although these reports carry the weight of practice rather than controlled measurement, they consistently identify coordination as particularly difficult for the work this thesis concerns. Yet an agent taking on a large task alone still encounters the accumulation described in Section~\ref{sec:background-context-windows-and-context-decay}. Its context grows, its reliability decays, and the cost of each step rises. The single agent and the coordinated team each face a difficulty the other does not.

\section{Frameworks on Top of a Coding Agent}
\label{sec:background-frameworks-on-top-of-a-coding-agent}

Multi-agent coordination nevertheless entered everyday development through external frameworks that organise the coding agents developers already use, rather than through the purpose-built research systems of Section~\ref{sec:background-multi-agent-systems}. Their natural-language instructions, role descriptions, and methodology guides shape how an existing agent approaches its work. The field has not agreed on a name for this class. This thesis refers to them as \emph{frameworks operating on top of a coding agent}.

How a framework on top of a coding agent coordinates several agents has changed as the coding agents themselves have evolved. At first, each coding agent ran in a separate conversation. The user organised those conversations, assigned each agent a role and task through explicit instructions, and carried work between them through shared files. At its introduction in April 2025, BMAD was a framework of this kind.\footnote{BMAD-METHOD repository: \url{https://github.com/bmad-code-org/BMAD-METHOD}.} It assigned a role to each agent so that they collaborated like members of a software development team.

Coding agents later gained the ability to delegate work to other agents launched into separate conversations. These delegated agents are known as \emph{subagents}. They receive work from and return their results to the agent that launched them, rather than requiring the user to coordinate each conversation directly. Newer frameworks were built around this lower-friction capability. Superpowers, for example, uses reusable natural-language files to teach a coding agent to divide work into tasks and dispatch subagents to execute and review them.\footnote{Superpowers repository: \url{https://github.com/obra/superpowers}.} Because the two arrangements are not exclusive, a framework may coordinate several user-facing agents while also using subagents within one or more of them.

\section{Agentic Project Management and the Research Gap}
\label{sec:background-agentic-project-management-and-the-research-gap}

This thesis presents and studies Agentic Project Management version 1 (APM v1). The author designed and built APM independently, first releasing it as open source in May 2025.\footnote{The APM release history is recorded in the repository's CHANGELOG: \url{https://github.com/sdi2200262/agentic-project-management}.} APM operates on top of an existing coding agent and combines the context-engineering strategies of Section~\ref{sec:background-spec-driven-development} and Section~\ref{sec:background-multi-agent-systems} by having several agents follow a spec-driven workflow. APM's May 2025 release predated Kiro in July and Spec-kit in September. Those later tools popularised \emph{spec-driven development} as the name for this kind of AI-assisted workflow.

APM has been revised continually as the coding agents beneath it and the underlying models improved. APM v1 is a ground-up redesign whose roles, workflow, artefacts, and file structure differ substantially from the earlier releases. The study used its v1.0.1 template release, published on 23 April 2026, with the matching \texttt{agentic-pm} command-line tool.\footnote{APM v1.0.1 release: \url{https://github.com/sdi2200262/agentic-project-management/releases/tag/v1.0.1}.}

One design choice persisted through that redesign: APM's coordination is user-mediated, with the user carrying communication among several agents in their own conversations. File-based protocols govern both communication among APM agents and the spec-driven workflow they follow. Chapter~\ref{chap:framework-design} will describe these architectural choices in full.\footnote{Forthcoming. Framework Design will define APM's design principles, roles, phases, Message Bus, memory, Handoff, and distribution.}

APM v1 has attracted visible interest in the open-source community,\footnote{On 17 June 2026, APM had roughly 2,300 stars on GitHub and its command-line tool had over 16,000 downloads from npm. By 18 July 2026, the readings were roughly 2,400 stars and over 19,000 downloads. These are indicative signals of community interest rather than measures of sustained use. APM repository: \url{https://github.com/sdi2200262/agentic-project-management}. \texttt{agentic-pm} npm package: \url{https://www.npmjs.com/package/agentic-pm}.} yet it has not been evaluated with developers at work. The studies of Section~\ref{sec:background-multi-agent-systems} measure programmatic multi-agent systems on benchmarks. Frameworks operating on top of coding agents remain outside their scope. To our knowledge, the closest human-in-the-loop work is a recent controlled study of OpenHands and GitHub Copilot \cite{chen2025codewith}. It used Copilot in the completion and chat form available at the time, so the comparison varies the degree of automation rather than framework coordination.

Existing work therefore leaves the effect of framework coordination untested among developers working with coding agents. We address this gap by comparing a workflow in which the user coordinates several agents through APM with a comparable spec-driven workflow carried out by one agent.
