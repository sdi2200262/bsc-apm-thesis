\section{AI Assistants and Agents}
\label{sec:ai-coding-assistants-and-agents}

The tools that assist developers as they write code have changed quickly, from completing a single line to carrying out whole tasks on their own. Integrated development environments have offered identifier and interface completion since the 1990s, and by the late 2010s those suggestions were ranked by machine-learning models trained on large code corpora. Such systems retrieve and rank symbols that already exist; they do not compose new code. The generative shift came when large language models (LLMs), whose training data includes large quantities of code, began producing novel, multi-line completions inline in the editor, the form that GitHub Copilot brought to a wide audience in 2021.\footnote{GitHub Copilot technical preview, June 2021: \url{https://github.blog/2021-06-29-introducing-github-copilot-ai-pair-programmer/}.} A second and distinct mode of interaction followed in late 2022, when general-purpose conversational assistants reached the public. While these were not explicitly coding tools, developers used them broadly, to explain unfamiliar code, stand in for documentation, or think through a problem as much as to draft a snippet to paste back. This conversational mode was soon folded into the editor, and then extended past advice and into action. These AI assistants started editing files, running commands, and revising their work against the results. Tools of this last kind, which act on a project rather than only commenting on it, emerged over 2024 and 2025.\footnote{Early examples include Devin, announced in March 2024 as an autonomous ``AI software engineer'' acting on a project from its own sandboxed environment rather than the developer's editor (\url{https://www.cognition.ai/blog/introducing-devin}), and GitHub Copilot's agent mode, introduced in February 2025, which works inside the editor to plan a task, edit across multiple files, run commands, and iterate on the results (\url{https://code.visualstudio.com/blogs/2025/02/24/introducing-copilot-agent-mode}).} It is this conversational line, rather than inline completion, that the systems studied in this thesis descend from.

We use the term \emph{agent} in a specific sense throughout this thesis. In its classical formulation, an agent is anything that perceives its environment through sensors and acts upon that environment through actuators \cite{russell2021aima}. Brought into the setting of LLMs, an agent is built around an LLM, with the ability to perceive and use external tools and resources, extending it beyond producing text into planning, memory, and action \cite{liu2024llmagents}. What distinguishes such an agent is where control of the process sits. The model itself drives the work, reasoning about the task and choosing its next action or tool in an interleaved loop \cite{yao2023react}, rather than following a predetermined sequence of steps that surrounding code fixes in advance. The frameworks evaluated in this thesis are \emph{agentic} in precisely this sense, the model rather than a fixed script driving the work.

Attempts to measure the effect of these tools on developer productivity have reached conflicting conclusions across different generations of the technology. Field experiments with an earlier generation of assistant reported substantial gains. In three randomised controlled trials conducted at Microsoft, Accenture, and a Fortune-100 company, nearly five thousand professional developers using an AI assistant completed around a quarter more tasks, with the clearest gains among the less experienced \cite{cui2026genai}. A later trial, conducted by METR in early 2025 with the Cursor editor\footnote{Cursor, an AI code editor: \url{https://cursor.com}.} using Claude 3.5 and 3.7 Sonnet, reached the opposite result. Experienced open-source developers working on large repositories they regularly contribute to were left roughly 19\% slower, even as those same developers expected to be sped up \cite{becker2025metr}. The two studies differ in the models they used, their tools, their tasks, and the developers they observed, so the effect reads as conditional rather than settled. Both, like the wider productivity literature of the field, ask only whether AI assistance helps; neither varies the workflow or framework through which a developer works with the agent, which is the dimension this thesis sets out to compare.

\section{Context Windows and Context Decay}
\label{sec:context-windows-and-context-decay}

Whatever its form, an agent is built on a model that reads and writes text in units called tokens, and can attend to only a bounded span of them at once. This span is the model's context window. Into it go the system prompt, the instructions the agent was given, the files, and tool output it has read, and its own earlier turns; a long task steadily consumes it. At the time of writing, a frontier model's context window spans several hundred thousand to a million tokens, yet even a window of that size can be exhausted by a real-world task that spans many steps.

A model does not even use the context it has evenly. Controlled experiments on long-context models found a U-shaped pattern. Performance is highest when the relevant information sits at the start or the end of the input and falls sharply when it lands in the middle, even for models built for long contexts \cite{nliu2023lostmiddle}. Usable capacity is therefore smaller than the raw token count suggests.

For an agentic coding session the consequence is direct. As the session proceeds, every file read, tool called, and command executed consumes context. As that context accumulates, the agent is likelier to forget earlier decisions, lose track of completed work, or drift from the original goal \cite{liu2024llmagents}. Summarising earlier context or retrieving it on demand buys room, but only by discarding detail, trading fidelity for space. The summarising form, replacing the accumulated context with a shorter version the session grows from again, is known as \emph{compaction} and is now common in AI assistants.

This accumulation also incurs a direct monetary cost. Each step runs the model over the entire session so far as input, and a call is priced by the number of tokens it processes, both the input it reads and the output it produces. Caching the repeated tokens from earlier in the session does lower their price, but caches are short-lived and expire, so it is an unreliable way to contain the growing cost. Every step therefore tends to cost more than the one before it, and the cumulative cost of a long task grows faster than the number of steps it takes \cite{gao2025turncontrol}.

Together, the decline in reliability and the climb in cost have made the deliberate management of the context window a concern in its own right. Early practice with these models centred on prompt engineering, the structuring of the natural-language input given to a model to draw out a particular response. As work grew into long agentic sessions, the harder question became less how a single request is phrased than what the context window should hold at each step of a task. This wider practice, managing the whole body of context supplied to a model so that an agent's limited attention and tokens fall where they count rather than draining away as a session drifts, is known as context engineering. The strategies described through the rest of this chapter are, in different ways, responses to it.

\section{Spec-Driven Development}
\label{sec:spec-driven-development}

One way to keep an agent on course is to set down a specification of what it should build before it builds it. This is a practice from traditional software engineering, well before AI. Design by Contract, described in 1992, makes the specification part of the program itself, attaching to each routine the conditions it assumes on entry, the guarantees it must meet on exit, and the invariants it preserves throughout \cite{meyer1992dbc}. Test-driven development (TDD), codified in 2002, inverts the usual order of coding and testing, writing the tests that define correct behaviour first, so that an executable specification of what the code must do precedes the code itself \cite{beck2002tdd}. The phrase \emph{specification-driven development} (SDD), now common in the AI field, was also in use in software engineering by 2004 for an approach that combined TDD with Design by Contract, treating tests and contracts as two complementary kinds of specification \cite{ostroff2004specdriven}. In this thesis, SDD refers to the current, AI-assisted sense, not the earlier one.

Yet early work with AI assistants usually took place without any kind of discipline, and the developers improvised instructions turn by turn. The intent of the work lived only in a lengthening conversation, easily lost as it grew and subject to all the faults we described above. Spec-driven development with agents carries the older idea forward, fixing intent in a durable artefact written before the code, a specification that the implementation is generated from and checked against rather than left to accumulate informally over a session. This connects back to the decay described earlier. A crucial instruction given only at the start of a conversation is soon buried under a growing context. It becomes a detail of a larger effort and the model attends to it least. A specification is a document the agent keeps returning to, a deliberate piece of context engineering that keeps the goal in view as the work proceeds.

As a named practice in AI-assisted development, SDD took shape over 2025. Amazon's Kiro, released in July, built its workflow around it, carrying a developer from natural-language requirements through a design to a sequenced list of tasks before any code is written.\footnote{Kiro, introduced in July 2025 with spec-driven development as its named workflow: \url{https://kiro.dev/blog/introducing-kiro/}.} GitHub's Spec-kit, released in September, set out the same idea as a sequence of stages that take a project from specifying through planning to implementing. It turns specifications into software on the premise that the \emph{spec}, not the code, is the source of truth.\footnote{GitHub Spec-kit, described as an open-source spec-driven development toolkit, September 2025: \url{https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/}.}

Amongst these early adopters and other popular open-source alternatives, SDD is the work of a single agent. These tools supply no agent of their own; they work through existing coding agents, guiding them through the stages of the workflow. Working with the developer, that single agent writes the specification and a plan, then implements against those documents.

\section{Multi-Agent Systems}
\label{sec:multi-agent-systems}

The SDD discipline described so far anchors a single agent by fixing intent in a specification it can return to. A different context-engineering strategy responds to the same accumulation problem by not relying on a single context window at all. Rather than letting one agent absorb the whole task, the work can be divided and shared among several agents, each given a smaller, self-contained part and working with its own separate context. Several such agents, working together on one task, form a multi-agent system (MAS). In practice, agents in a MAS coordinate by passing results or messages between them.

The appeal is straightforward. No single context window holds the whole task, independent parts can proceed in parallel, and each agent can be specialised to its role. However, whether distributing the work this way actually produces better software than a single capable agent is far from settled.

Multi-agent systems have a long history in artificial intelligence, where they describe collections of autonomous entities that act within a shared environment \cite{russell2021aima}. The arrival of capable language models prompted a wave of research that applied the idea to them. Over 2023 several systems organised LLM-based agents into role-specialised teams that collaborated on software tasks. CAMEL paired agents in a structured dialogue \cite{li2023camel}, ChatDev cast them as the staff of a virtual software company \cite{qian2024chatdev}, and MetaGPT coordinated them through the documents and standard procedures of a development process \cite{hong2024metagpt}. AutoGen, an open-source programming framework built by Microsoft, was used to build such collaborative conversations between agents to solve complex problems and write code \cite{wu2024autogen}. These early systems share a common form. Each is a program that orchestrates calls to a model through its programming interface, so the agents exist only within the surrounding code that drives them.

The evidence that this approach improves performance compared to a single agent is weak. A study of why such systems fail collected the execution traces of seven widely used multi-agent frameworks, including three of the ones presented above. It found failure rates between roughly forty and ninety per cent across more than two hundred tasks. The breakdowns were traced to problems of specification, misaligned communication between agents, and inadequate checking of results, and reported that the gains over a single agent are often minimal \cite{cemri2025masfail}. A separate empirical comparison reaches a complementary conclusion. It finds that the advantage of a MAS over a single agent narrows as the underlying model grows more capable, so that much of the benefit seen with weaker models recedes with stronger ones \cite{gao2025singlemulti}. Taken together, these results suggest that the improvement the division of labour promises is neither reliably delivered nor stable as the models themselves improve.

The same caution appears in the experience of those building agents for developing software in particular. An article from Anthropic describing a multi-agent research system reports a large gain over a single agent on open-ended research, but it attributes that gain to the breadth of parallel search the task allows, and singles out coding as a poor fit. Most coding work, it notes, divides into fewer genuinely independent pieces and depends on context that every agent would need to share.\footnote{Anthropic, ``How we built our multi-agent research system'', 13 June 2025: \url{https://www.anthropic.com/engineering/multi-agent-research-system}.} Another article from Cognition, the team behind the Devin coding agent mentioned earlier, argues against multi-agent designs for coding, holding that splitting the work disperses decisions and prevents agents from sharing enough context, which leaves the resulting systems fragile.\footnote{Cognition, ``Don't Build Multi-Agents'', 12 June 2025: \url{https://cognition.ai/blog/dont-build-multi-agents}.} Reports of this kind carry the weight of practice rather than controlled measurement, but together they make a consistent case that the difficulties of coordination fall hardest on the kind of work this thesis concerns. Yet these claims have their own weaknesses. An agent taking on a large task on its own still encounters the accumulation described in Section~\ref{sec:context-windows-and-context-decay}, where context grows, reliability decays, and the cost of each step climbs. The single agent and the coordinated team each face a difficulty the other does not.

Despite this discouraging record, multi-agent coordination took hold in everyday development all the same, in frameworks that took a different form from the research systems traced here.

\section{Frameworks on Top of a Coding Agent}
\label{sec:frameworks-on-top-of-a-coding-agent}

The frameworks seen so far stand in two different relations to the agent. The multi-agent systems of Section~\ref{sec:multi-agent-systems} are programs written against a model's interface, where the agents exist only within the code that drives them. The spec-driven tools of Section~\ref{sec:spec-driven-development} instead work through an existing coding agent, shaping how it behaves with sets of natural-language files, the instructions, role descriptions, and methodology guides it reads and follows as it works. This second form has become the common one in everyday software development. It covers the single-agent spec-driven tools already described and, alongside them, frameworks that coordinate several agents at once. The field has not agreed on a name for this class; in this thesis they are referred to as frameworks operating on top of a coding agent.

How a framework of this kind coordinates several agents has changed as the tools beneath it have evolved. The earliest such frameworks appeared before the coding agents offered any way to coordinate more than one agent at once, so coordination was arranged by hand. The developer opened several agents at the same time, each in its own conversation and given a role, and carried work between them through shared files. BMAD, an agile development framework of this kind, arrived in this period, in April 2025.\footnote{BMAD-METHOD: \url{https://github.com/bmad-code-org/BMAD-METHOD}.} It assigns a role to each agent, so they collaborate in a way that mimics a real software development team.

Once the coding agents gained the ability to spawn subagents of their own, the developer could ask the main agent to delegate to these subagents directly rather than opening separate agents by hand. Newer frameworks were built around this capability and the low friction it brought. Superpowers, for example, is a subagent-driven framework that organises development through natural-language files that hold reusable instructions and teach the main agent to break the work into tasks, then dispatch subagents to carry out and review them.\footnote{Superpowers: \url{https://github.com/obra/superpowers}.} The two arrangements are not exclusive, and a single framework may open several separate agents, dispatch subagents from within one, or do both.

\section{Agentic Project Management and the Research Gap}
\label{sec:agentic-project-management-and-the-research-gap}

This thesis studies one such framework, Agentic Project Management (APM). At its first prototype release it was, to our knowledge, among the first to operate on top of an existing coding agent. It combined the two context-engineering strategies of Section~\ref{sec:spec-driven-development} and Section~\ref{sec:multi-agent-systems} at once: a MAS following a spec-driven workflow. It was first released in May 2025,\footnote{The APM release history is recorded in the repository's CHANGELOG: \url{https://github.com/sdi2200262/agentic-project-management}.} well before the coding agents could coordinate subagents natively,\footnote{Claude Code was, as far as we are aware, the first interactive coding agent to do so, introducing subagents in July 2025; others followed. See the repository's CHANGELOG: \url{https://github.com/anthropics/claude-code}.} and before spec-driven development was named and popularised by tools such as Kiro and Spec-kit.

APM has been revised continually since, as both the coding agents beneath it and the underlying models improved in parallel. The version this thesis presents is a more recent, ground-up redesign, released as version 1.0 in April 2026.\footnote{APM version 1.0.0 release: \url{https://github.com/sdi2200262/agentic-project-management/releases/tag/v1.0.0}.} It shares a backbone with every version since the first release: the MAS is formed by several main agents whose communication passes through the user, rather than by one main agent dispatching the rest as subagents. Each main agent may still dispatch subagents of its own, a platform capability available to any agent, separate from the user-mediated coordination that defines APM. Both their coordination and the spec-driven methodology they follow are governed by file-based protocols. These are opinionated architectural choices, and the next chapter describes the design in full.

APM has seen genuine uptake in the open-source community,\footnote{As of the middle of June 2026, APM had roughly 2,300 stars on GitHub and its command-line tool had been downloaded over 16,000 times from npm. These are indicative signals of community interest rather than measures of sustained use.} yet it has not been evaluated with developers at work. The evidence assembled in this chapter does not settle the question its design raises: whether coordinating several agents in this way produces better software than a single agent following a comparable spec-driven discipline. The studies of Section~\ref{sec:multi-agent-systems} concern programmatic multi-agent systems measured on benchmarks, not the frameworks that operate on top of a coding agent which developers now use. To our knowledge, the closest human-in-the-loop work, a recent controlled study, sets GitHub Copilot, an autocomplete-and-chat assistant, against a more autonomous agent \cite{chen2025codewith}; its concern is the degree of automation, a different question from ours.

In this thesis, we present APM as a framework and evaluate it through a comparative case study against GitHub's Spec-kit, a leading single-agent spec-driven counterpart introduced in Section~\ref{sec:spec-driven-development}.\footnote{Spec-kit had over 110,000 stars on GitHub as of the middle of June 2026.} With the spec-driven discipline and the coding agent shared between them, the comparison isolates what distinguishes APM: splitting the work across several agents in place of one, and its own realisation of that discipline.
