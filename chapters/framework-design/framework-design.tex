\section{Design Goals}
\label{sec:framework-design-goals}

APM is a framework operating on top of a coding agent. It uses several such agents to form a MAS intended for substantial, real-world software development projects. Its design limits context accumulation by dividing a project across separate agent conversations and giving each agent a distinct responsibility. One plans the project, producing a durable account of what to build and how to build it. Another maintains the project-wide view by distributing bounded parts of the work to others and reviewing what they produce.

That division, however, also separates the knowledge and decisions needed to keep the agents' contributions consistent with what they should collectively produce. To address this separation, APM uses shared files to make that information persistent and available across conversations. They hold project intent, execution state, and information exchanged among agents, while explicit protocols define what each agent reads and writes.

Beyond coordinating its agents, APM aims to preserve user authority over development and agent interaction. The user holds final authority over project decisions and carries all communication between conversations. Review points of the workflow keep planning, coordination, and execution visible and open to intervention.

\section{Agent Roles}
\label{sec:framework-design-agent-roles}

APM organises its agents into three roles: the \emph{Planner}, \emph{Manager}, and \emph{Worker}. Each is a coding agent operating in its own conversation under role-specific instructions. Those instructions define the agent's responsibilities, workflow, and protocols, which determine the project information its conversation needs to hold. Planning involves one Planner, while implementation involves one Manager at a time and one or more Workers. Each retains the coding agent's ordinary tools, access permissions, and ability to dispatch subagents. Their specialisation comes from scoping the context that reaches them.

The Planner does research, resolves requirements and design choices with the user, and records the result in three planning documents. The \emph{Spec} defines what to build. The \emph{Plan} divides implementation into bounded units of work called \emph{Tasks}, organised by domain. The \emph{Rules} govern how their execution is carried out. The Planner's participation ends when implementation begins, leaving its conversation's full context window available to develop these documents.

The Manager coordinates implementation at project level. It distributes Tasks to Workers and supplies the context required to execute them. It reviews their results, maintaining the planning documents and project state that form its context alongside Task outcomes. The instructions the Manager receives establish its usual focus, while review or investigation may take it into code or execution detail.

Each Worker is assigned the Tasks of one domain from the Plan, which it executes and validates. For each Task, the Manager provides a self-contained assignment. Workers follow the Rules. Across successive Tasks, accumulated context allows the Worker to develop familiarity with that part of the project. After each Task, the Worker records its outcome and reports it to the Manager.

\section{Agent Orchestration}
\label{sec:framework-design-agent-orchestration}

The Planner produces its three planning documents through iteration with the user. Its accumulated context does not pass into implementation: the Manager receives the finished Spec, Plan, and Rules, while Workers consult only the Rules.

For each Task, the Manager constructs a \emph{Task Prompt} carrying the Task-specific information required for execution. It draws planned requirements from the Spec and Plan and adds context from relevant earlier contributions. Familiarity determines the detail: a pointer may recall a Worker's own output, while another Worker's contribution requires what it produced, where it resides, and how the Task depends on it. After carrying out the work, Workers return a \emph{Task Report} of the outcome.

The Manager can distribute Tasks individually, combine several Tasks for one Worker as a batch, or send independent Tasks to different Workers concurrently, processing Task Reports as they arrive. Dependencies among Tasks constrain these arrangements.

These exchanges use a file-based \emph{Message Bus}. Each Worker has a \emph{Task Bus}, where the Manager writes its Task Prompts, and a \emph{Report Bus}, where the Worker writes its Task Reports. Figure~\ref{fig:framework-design-message-bus} maps these two directions of exchange. A bus file is empty or holds one message awaiting delivery. Its recipient clears the file after processing that message, before the channel is reused. The user serves as the mediator between the separate conversations: when an agent writes to a bus file, it informs the user, who can inspect and review the content, returning corrections as needed, before directing the recipient to read it.

These intervention points are deliberate. They let the user exercise final authority as decisions and results pass between agents, allowing mistakes or unwanted directions to be addressed before they propagate through the project.

\section{State Management}
\label{sec:framework-design-state-management}

The planning documents define the intended work, but execution may reveal that they need to change. The Manager can revise them within the project's established direction and Workers may propose changes to the Rules. Changes to direction or scope, however, require explicit user approval.

During implementation, the Manager also maintains documents for coordination and project history. The \emph{Tracker} holds its live account of coordination state, recording Task and Worker status, and working notes accumulated during execution. These notes hold pending considerations and findings that may affect later decisions. \emph{Memory} is a hierarchically organised collection of files that preserves project history. Its \emph{Index} provides the overview: project-level summaries with references to their underlying records, and durable observations distilled from the Tracker's working notes, including established patterns, preferences, and project-level insights.

After completing a Task, its Worker writes a \emph{Task Log} that reduces accumulated execution detail to what the Manager needs for coordination: the outcome, validation, deliverables, file changes, and findings bearing on the wider project. The Task Report briefly announces the results through the Message Bus, and points to the corresponding Task Log for review.

Condensing execution and coordination detail is what allows the Manager to oversee several Workers, dispatch and review many Tasks, and maintain APM's project state without accumulating context excessively. Figure~\ref{fig:framework-design-state-reduction} summarises how both enter Memory.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{assets/figures/framework-design/state-reduction.pdf}
  \caption{Reduction of execution and coordination detail into persistent project history. Task outcomes are recorded in Task Logs which are later condensed into completed-work summaries, while Tracker working notes are distilled into durable observations in the Index.}
  \label{fig:framework-design-state-reduction}
\end{figure}

The user invokes a \emph{Handoff} on demand to transfer a role from an agent conversation carrying accumulated context to a fresh one. The outgoing agent follows the framework's instructions to record what must carry over in two documents. The \emph{Handoff Log} records past work, decisions, and working knowledge not held in Task Logs, and joins them in Memory. The \emph{Handoff Prompt} describes the current state and tells the incoming agent what to read and do next. The user carries it through the role's \emph{Handoff Bus}. The incoming agent rereads its role instructions, then uses both documents and relevant project files to resume from where the outgoing agent left off. Figure~\ref{fig:framework-design-handoff} traces the transfer.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{assets/figures/framework-design/handoff.pdf}
  \caption{Handoff between outgoing and incoming agent conversations. The outgoing agent records a Handoff Log in Memory and sends a Handoff Prompt through its Handoff Bus. The incoming agent reads both with the other project state needed to resume the role.}
  \label{fig:framework-design-handoff}
\end{figure}

A conversation approaching its context window limit is the usual occasion for a Handoff, but the user can invoke one earlier to reduce cost or try to restore performance. The system hosting the agent can also reset accumulated context through compaction, described in Section~\ref{sec:background-context-windows-and-context-decay}, but the resulting summary is ephemeral to the conversation. If the conversation fills again, the next compaction summarises that summary together with the context accumulated since, further reducing the detail retained from earlier work. A Handoff instead records the transfer in persistent files, so successive Handoffs retain a durable history of the role's work.

When an agent loses its working state without having performed a Handoff, the user can invoke APM's recovery procedure. The agent then rereads its role instructions and relevant project files to restore the framework's procedures and establish where its work stands.

At project completion or a pause, APM can archive all files that hold project state and optionally add a summary of their scope, outcomes, decisions, deliverables, and issues. A later Planner can inspect a relevant archive to inform project research and planning.

\section{Workflow}
\label{sec:framework-design-workflow}

APM exposes its workflow through structured documents and commands. Its artefacts use Markdown, often paired with YAML fields that identify state and determine procedural branches. Across the coding-agent platforms it supports, APM packages each command as a pre-written prompt and adapts its invocation syntax to the platform. Table~\ref{tab:framework-design-commands} uses their common slash-prefixed form. The user invokes each command in the appropriate conversation, making transitions among separate conversations explicit user actions.

APM's workflow has two phases. The planning phase produces the planning documents, and the implementation phase executes the work they define.
