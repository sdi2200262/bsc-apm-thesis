\section{Design Goals}
\label{sec:framework-design-goals}

APM is a framework operating on top of a coding agent. It uses several such agents to form a MAS intended for substantial, real-world software development projects. Its design limits context accumulation by dividing a project across separate agent conversations and giving each agent a distinct responsibility: one plans the project, one distributes the work and reviews what comes back, and the rest carry it out.

Partitioning responsibilities across conversations, however, also separates the knowledge and decisions needed to keep the agents' contributions consistent with what they should collectively produce. To address this separation, APM uses shared files to make that information persistent and available across conversations. They hold project intent, execution state, and information exchanged among agents, while explicit protocols define what each agent reads and writes.

Beyond coordinating its agents, APM aims to preserve user authority over development and agent interaction. The user holds final authority over project decisions and carries all communication between conversations. Review points of the workflow keep planning, coordination, and execution visible and open to intervention.\ethan{How is this different from standard harnesses like Claude Code? APM organises its agents into three roles: the \emph{Planner}, \emph{Manager}, and \emph{Worker}, summarised in Table~\ref{tab:framework-design-agent-roles}. Each is a coding agent operating in its own conversation under role-specific instructions. Those instructions define the agent's responsibilities, workflow, and protocols, which determine the project information its conversation needs to hold. Planning involves one Planner, while implementation involves one Manager at a time and one or more Workers. Each retains the coding agent's ordinary tools and access permissions. Their specialisation comes from scoping the context that reaches them.

The Planner does research, resolves requirements and design choices with the user, and records the result in three planning documents. The \emph{Spec} defines what to build. The \emph{Plan} divides implementation into bounded units of work called \emph{Tasks}, organised by domain. The \emph{Rules} govern how their execution is carried out. The Planner's participation ends when implementation begins, leaving its conversation's full context window available to develop these documents.

The Manager coordinates implementation at project level. It distributes Tasks to Workers and supplies the context required to execute them. It reviews their results, maintaining the planning documents and project state that form its context alongside Task outcomes. The instructions the Manager receives establish its usual focus, while review or investigation may take it into code or execution detail.

Each Worker is assigned the Tasks of one domain from the Plan, then executes and validates them. Workers follow the Rules. Across successive Tasks, its accumulated context builds familiarity with that part of the project.

When investigation or debugging threatens to consume a conversation's context, the agent launches platform-native subagents. Their findings return to the role's conversation for verification and integration.

\section{Agent Orchestration}
\label{sec:framework-design-agent-orchestration}

For each Task, the Manager constructs a \emph{Task Prompt}\ethan{it would be nice if these terms were defined somewhere in the background}\me{I believe domain primitives belong in the chapter where they originate, similar to my note in chapters/evaluation/evaluation.tex:106. Familiarity determines the detail: a pointer may recall a Worker's own output, while another Worker's contribution requires what it produced, where it resides, and how the Task depends on it. After carrying out the work, Workers return a \emph{Task Report} of the outcome.

The Manager can\ethan{again avoid "Can" - when does the manager dispatch? who allocates the workers? how is work allocation determined?} distribute Tasks individually, combine several Tasks for one Worker as a batch, or send independent Tasks to different Workers concurrently, processing Task Reports as they arrive. These exchanges use a file-based \emph{Message Bus}\ethan{Will you define the protocol/data formats exchanged through the various buses?}. Its recipient clears the file after processing that message, before the channel is reused. The user serves as the mediator between the separate conversations: when an agent writes to a bus file, it informs the user, who can inspect and review the content, returning corrections as needed, before directing the recipient to read it.

These intervention points are deliberate. They let the user exercise authority as decisions and results pass between agents, allowing mistakes or unwanted directions to be addressed before they propagate through the project.

\section{State Management}
\label{sec:framework-design-state-management}

The planning documents define the intended work, but execution may reveal that they need to change. The Manager can revise them within the project's established direction and Workers may propose changes to the Rules. Changes to direction or scope, however, require explicit user approval.

During implementation, the Manager also maintains documents for coordination and project history. The \emph{Tracker}\ethan{Where is the "Tracker" definied? How is it different from version control? Every single term that's shown should be part of a starting architecture diagram and as a component it should be defined somewhere in the text.} holds its live account of coordination state, recording Task and Worker status, and working notes accumulated during execution. These notes hold pending considerations and findings that may affect later decisions. \emph{Memory} is a hierarchically organised collection of files that preserves project history. Its \emph{Index} provides the overview: summaries of completed work with references to their underlying records, and durable observations distilled from the Tracker's working notes, including established patterns, preferences, and project-level insights.

After completing a Task, its Worker writes a \emph{Task Log} that reduces accumulated execution detail to what the Manager needs for coordination: the outcome, validation, deliverables, file changes, and findings bearing on the wider project. The Task Report briefly announces the results through the Message Bus, and points to the corresponding Task Log for review.

The user invokes a \emph{Handoff}\ethan{Is handoff defined above? again, should be introduced in that high-level diagram in the beginning} on demand to transfer a role from an agent conversation holding accumulated context to a fresh one. The outgoing agent follows the framework's instructions to record what must carry over in two documents. The \emph{Handoff Log} records past work, decisions, and working knowledge not held in Task Logs, and joins them in Memory. The \emph{Handoff Prompt} describes the current state and tells the incoming agent what to read and do next. The user carries it through the role's \emph{Handoff Bus}. The incoming agent rereads its role instructions, then uses both documents and relevant project files to resume from where the outgoing agent left off. A conversation approaching its context window limit is the usual occasion for a Handoff, but the user can invoke one earlier to reduce cost or try to restore performance. The system hosting the agent can also reset accumulated context through compaction, described in Section~\ref{sec:background-context-windows-and-context-decay}, but the resulting summary is ephemeral to the conversation. If the conversation fills again, the next compaction condenses it together with the context accumulated since, further reducing the detail retained from earlier work. A Handoff instead records the transfer in persistent files, so successive Handoffs retain a durable history of the role's work.

When an agent loses its working state without having performed a Handoff, the user can invoke APM's recovery procedure. The agent then rereads its role instructions and relevant project files to restore the framework's procedures and establish where its work stands.

At project completion or a pause, APM can archive all files that hold project state and optionally add a document summarising their scope, outcomes, decisions, deliverables, and issues. A later Planner can use APM's custom archive-research subagent to inspect a relevant archive and inform project research and planning.

\section{Workflow}
\label{sec:framework-design-workflow}

APM exposes its workflow through structured documents and commands. Its artefacts use Markdown, often paired with YAML fields that identify state and determine procedural branches. APM packages each command as a pre-written prompt and adapts its invocation syntax to each coding-agent platform it supports. Each command establishes a role and points the agent to the procedures its next step requires. Detailed procedures live in separate guides, each addressed to a single role, which the agent reads when it reaches the step that needs one. Instructions shared across roles, such as the Message Bus protocols, are packaged as skills.\footnote{Agent Skills is an open standard, originally developed by Anthropic, for packaging instructions and resources that agents load as needed: \url{https://agentskills.io}.}

APM's workflow has two phases. The planning phase produces the planning documents, and the implementation phase executes the work they define.

\subsection{Planning Phase}
\label{sec:framework-design-planning-phase}

Planning begins with the Planner building an understanding of the project. It reads the materials the user identifies as authoritative and explores any codebase the project involves before questioning the user, so its questions address what remains unknown. The Planner may delegate substantial codebase research to subagents, then verifies their findings before using them in its questions or planning documents. Successive rounds go deeper, covering the project's purpose and deliverables, then its technical requirements and dependencies, then the constraints, standards, and conventions under which the work should be carried out. Where research or the user's answers open more than one viable approach, the Planner presents the alternatives with their trade-offs and the user chooses.

The questioning ends with a consolidated account of the Planner's understanding, and planning advances only once the user approves it. Corrections send the Planner back to the material: it applies what the user raised, asks whatever the correction opens up, and presents the revised account again.

The Planner then produces the Spec, the Plan, and the Rules, one at a time. It presents its reasoning for each in the conversation before writing it, and each document passes through that same review cycle before the next begins. Written against each other in turn, the three hold one account of the project.

The Spec records the decisions that shape what is built: the choice made, the alternatives it displaced, and the constraints that bound it. Its structure follows the project's concerns, and where the user's documents already define a requirement it references them instead of restating it. Decisions are kept separable so the Manager can extract the ones a given Task needs.

The Plan organises the work. It divides the project into domains, assigns a Worker to each, and defines for every Task what it delivers, the criteria that validate it, and the previous Tasks it depends on. It then sequences those Tasks into \emph{Stages}, each delivering a coherent part of the project, beginning only after the preceding one completes. Within a Stage, a Task waits for the ones it depends on, while those whose dependencies are complete can proceed together. Parallel work therefore happens only within a Stage, as Figure~\ref{fig:framework-design-stage-progression} shows.

The Rules hold the execution patterns that apply across all or most Tasks, such as coding conventions and quality standards. Every Worker receives the same Rules, yet a requirement is not a Rule merely because it reaches every Worker: an output format or interface contract belongs to the Spec.

\subsection{Implementation Phase}
\label{sec:framework-design-implementation-phase}

Implementation begins with the Manager reading the planning documents and presenting its understanding of the project and the conventions it will work under. It dispatches the first Task once the user approves.

A Task is ready when the Tasks it depends on are complete. Its Worker works from the Task Prompt, the Rules, whatever it needs from the project's files, and the context it has accumulated over earlier Tasks. It executes the work and validates it against the Task's criteria, iterating where validation fails and pausing for the user where a criterion needs the user's judgement or an action outside the development environment. A difficult failure may be delegated to a debugging subagent, whose findings the Worker verifies before applying them. It then reports the outcome it reached: the Task complete, partial progress where iteration stalled, or a failure.

The Manager reviews the Task Report and the Task Log. An outcome short of complete, or a Worker's note that execution touched something beyond its Task, prompts investigation before anything is accepted. The Manager handles contained checks directly and may delegate context-intensive investigation to a subagent. Its findings decide among three outcomes. The work stands as it is, the Worker retries under a refined Task Prompt, or the planning documents need updating, as Section~\ref{sec:framework-design-state-management} describes. In each case the Manager records the result in the Tracker and reassesses which Tasks have become ready. Figure~\ref{fig:framework-design-task-cycle} follows one Task through this cycle.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{assets/figures/framework-design/task-cycle.pdf}
  \caption{One Task through the implementation cycle. The Task Prompt and the Task Report travel through the Message Bus, while the Task Log is written to Memory and reviewed from there.}
  \label{fig:framework-design-task-cycle}
\end{figure}

The Manager uses version control to keep each dispatched Task's work separate. At the start it establishes with the user which repositories the work targets and what branch and commit conventions each follows. Work for a dispatched Task goes on its own branch off the agreed base of the repository it touches, and concurrent Workers each get an isolated working copy of it through a git worktree. Workers commit their own work, while merging belongs to the Manager alone. This way work lands on the base branch only after passing the user who mediated its report and the Manager who reviewed and accepted it.

When every Task of a Stage is complete, the Manager closes it by writing a summary into Memory's Index and distilling the working notes the Stage accumulated. Those with lasting value join the Index as durable observations, those the next Stage still needs stay in the Tracker, and the rest are cleared. The Manager then opens the next Stage. When no Stage remains, the Manager records the project as complete, presents an account of what was built, and offers to archive the project state with a summary of its outcome.

\section{Distribution and Customisation}
\label{sec:framework-design-distribution-customisation}

APM keeps a single platform-neutral source of commands, guides, skills, subagent definitions, and project artefacts as templates in its GitHub repository.\footnote{APM repository: \url{https://github.com/sdi2200262/agentic-project-management}.} Coding-agent platforms differ in where and how they accept these documents. During a release build, the build system inserts each platform's unique paths, formats, and syntax into the templates, and the resulting packages are published in a GitHub Release with a manifest identifying which package belongs to each supported platform.

A command-line tool, \texttt{agentic-pm}, provides the user interface to this distribution. It is released separately through npm.\footnote{\texttt{agentic-pm} package: \url{https://www.npmjs.com/package/agentic-pm}.} The user selects a platform; the tool fetches a compatible release, resolves the corresponding package from its manifest, and scaffolds it into the project's workspace. It records the source and release for later updates. The tool and templates follow independent semantic versioning, with only the major version shared for compatibility.

The same architecture also makes the workflow customisable. Within their own copy or fork of the repository, users can extend or adapt any part of the framework's workflow, protocols, and procedures. The build system turns that custom source into platform packages and a release manifest that users can publish as their own GitHub Release. Through its custom-repository interface, the command-line tool fetches and scaffolds these releases in the same way as the official distribution.

Two official variants demonstrate this extension surface. APM Auto\footnote{APM Auto repository: \url{https://github.com/sdi2200262/apm-auto}.} replaces the original workflow's separate, user-mediated Worker conversations with Worker subagents launched directly by the Manager. APM Semi\footnote{APM Semi repository: \url{https://github.com/sdi2200262/apm-semi}.} retains the original workflow but gives the user more control by letting them claim any Task to complete themselves, with the assigned Worker standing by for assistance and validation.
